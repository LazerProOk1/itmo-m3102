# Структуры и объединения в C++

## Точки: зачем нужны структуры

Рассмотрим задачу: нужно хранить и передавать координаты точек на плоскости. Самый наивный способ — завести отдельные переменные для каждой координаты:

```cpp
#include <iostream>

void PrintPoint(int x, int y) {
    std::cout << '(' << x << ", " << y << ")\n";
}

int main() {
    int first_x = 10;
    int first_y = 20;
    int second_x = 200;
    int second_y = 300;

    PrintPoint(first_x, first_y);
    PrintPoint(second_x, second_y);
    PrintPoint(first_x, second_y); // Смешали координаты разных точек.
}
```

:::warning
Компилятор не знает, что `first_x` и `first_y` образуют одну точку, а `second_x` и `second_y` — другую. Это знание существует только в голове программиста. Поэтому вызов `PrintPoint(first_x, second_y)` — явная логическая ошибка, но компилятор её не заметит: с точки зрения типов это просто два независимых `int`, и передать в функцию можно любую их комбинацию.
:::

Чем больше в программе таких «связанных по смыслу, но разделённых в коде» переменных, тем выше риск случайно перепутать их местами. Решение — объединить связанные поля в один пользовательский тип. Для этого в C++ служат **структуры**.

## 1. Структуры

:::meaning
**Структура** (`struct`) — пользовательский тип данных, объединяющий несколько именованных полей (переменных разных или одинаковых типов) в единый объект.
:::

Перепишем пример с точками через структуру: теперь координаты одной точки передаются и хранятся вместе, как единое целое.

```cpp
#include <iostream>

struct Point {
    int x;
    int y;
};

void PrintPoint(Point point) {
    std::cout << '(' << point.x << ", " << point.y << ")\n";
}

int main() {
    Point first{10, 20};
    Point second{200, 300};

    PrintPoint(first);
    PrintPoint(second);
}
```

Здесь `Point` — новый тип, а `first` и `second` — его объекты («экземпляры»). Функция `PrintPoint` теперь принимает один параметр типа `Point`, и перепутать координаты разных точек местами уже физически сложнее: чтобы это сделать, нужно явно взять поле `x` от одной точки и `y` от другой, а не просто передать не тот аргумент.

### Инициализация структур

Структуру можно инициализировать несколькими способами. Рассмотрим их на примере:

```cpp
#include <iostream>

struct Point {
    int x;
    int y;
};

int main() {
    Point first{};                 // x == 0, y == 0.
    Point second{200, 300};         // Значения по порядку полей.
    Point third{.x = 10, .y = 20}; // Имена полей, C++20.
    Point fourth;                  // Поля не инициализированы.
    fourth = {30, 40};             // Задаём значения перед чтением.

    // Ошибки в стандартном C++20:
    // Point reversed{.y = 20, .x = 10};
    // Point mixed{10, .y = 20};

    std::cout << first.x << ' ' << first.y << '\n';
    std::cout << second.x << ' ' << second.y << '\n';
    std::cout << third.x << ' ' << third.y << '\n';
    std::cout << fourth.x << ' ' << fourth.y << '\n';
}
```

Разберём каждый вариант:

- **`Point first{};`** — инициализация пустыми фигурными скобками. Все поля получают значение по умолчанию: для `int` это `0`. Итог: `first.x == 0`, `first.y == 0`.
- **`Point second{200, 300};`** — позиционная инициализация. Значения присваиваются полям в том порядке, в котором поля объявлены в структуре: первое значение — `x`, второе — `y`.
- **`Point third{.x = 10, .y = 20};`** — инициализация с указанием имён полей (**designated initializers**), появившаяся в C++20. Здесь явно видно, какое значение какому полю присваивается, что делает код нагляднее, особенно если полей много.
- **`Point fourth;`** — объявление без инициализации фигурными скобками. Поля остаются неинициализированными: в них лежит «мусор» — случайные значения, оставшиеся в памяти. Читать такие поля до присваивания им значения нельзя. Именно поэтому сразу следующей строкой идёт `fourth = {30, 40};` — значения задаются до первого чтения.

:::warning
В стандартном C++20 при использовании именованных инициализаторов действуют два ограничения:
1. Поля обязательно перечисляются **в том же порядке**, в котором они объявлены в структуре. Поэтому `Point reversed{.y = 20, .x = 10};` — ошибка компиляции: `y` объявлен после `x`, а в инициализаторе указан первым.
2. Нельзя **смешивать** именованные и позиционные инициализаторы в одном выражении. Поэтому `Point mixed{10, .y = 20};` тоже не скомпилируется.

При этом пропускать поля можно: например, `Point{.y = 5}` допустимо, и тогда `x` получит значение по умолчанию (`0`).
:::

### Доступ к полям

Для обращения к полю обычного объекта (не через указатель) используется оператор точки `.`:

```cpp
#include <iostream>

struct Point {
    int x;
    int y;
};

int main() {
    Point point; // Поля не инициализированы — задаём значения перед чтением.
    point.x = 200;
    point.y = 250;

    std::cout << point.x << ' ' << point.y << '\n';

    return 0;
}
```

Здесь `point.x` читает и записывает конкретное поле `x` объекта `point`. Обратите внимание: объект `point` объявлен без инициализации, поэтому его поля сначала явно записываются (`point.x = 200;`, `point.y = 250;`), и только потом читаются в `std::cout`. Если бы поля читались раньше присваивания, программа обращалась бы к неинициализированной памяти.

### Вложенные структуры

Полем структуры может быть объект другого пользовательского типа. Так из простых компонентов собираются более сложные модели данных:

```cpp
#include <iostream>

struct Point {
    int x;
    int y;
};

struct Rectangle {
    Point left_top;
    Point right_bottom;
};

int main() {
    Rectangle rectangle{
        .left_top = {0, 100},
        .right_bottom = {200, 0},
    };

    rectangle.left_top.x = 10;
    std::cout << rectangle.left_top.x << '\n';

    return 0;
}
```

:::meaning
Выражение `rectangle.left_top.x` — это **цепочка обращений к полям**: сначала у объекта `rectangle` выбирается поле `left_top` (объект типа `Point`), а затем у *этого* объекта выбирается поле `x` (уже `int`). Оператор `.` применяется последовательно, слева направо.
:::

Здесь `Rectangle` описывается через два объекта `Point` — левый верхний и правый нижний углы прямоугольника. Такая вложенность позволяет переиспользовать уже определённый тип `Point`, не дублируя описание координат.

### Группировка полей

Тот же приём вложенности удобен для группировки логически связанных полей внутри более крупной структуры:

```cpp
struct Position {
    int x;
    int y;
};

struct Size {
    std::size_t width;
    std::size_t height;
};

struct Button {
    Position position;
    Size size;
};

Button button{
    .position = {0, 100},
    .size = {400, 80},
};
```

Вместо того чтобы хранить в `Button` четыре независимых поля (`x`, `y`, `width`, `height`), их группируют в два осмысленных подобъекта — `position` и `size`. Это делает код структуры понятнее: сразу видно, какие поля относятся к позиции кнопки, а какие — к её размеру.

## 2. Операции со структурами

Для структуры компилятор автоматически генерирует операции копирования и присваивания «по умолчанию» — они последовательно обрабатывают каждое поле структуры:

```cpp
Point first{1, 2};
Point second = first;

second.x = 10;
first = second;
```

Здесь `Point second = first;` копирует оба поля (`x` и `y`) из `first` в `second`. После этого `second.x = 10;` изменяет только копию — поле `x` в `second`, но не трогает `first`. Затем `first = second;` присваивает `first` новые (уже изменённые) значения полей `second`.

:::note
Если **все** поля структуры можно копировать, то и структура целиком — копируемый тип. Как следствие, у объектов такой структуры можно брать адрес, передавать их в функции по значению и возвращать по значению из функций — точно так же, как это делается со встроенными типами (`int`, `double` и т. д.).
:::

### Структуры в функциях

Структуры можно передавать в функции и возвращать из них по значению, как обычные объекты:

```cpp
#include <iostream>

struct Point {
    int x;
    int y;
};

Point MakePoint(int x, int y) {
    return Point{.x = x, .y = y};
}

Point Add(Point left, Point right) {
    return Point{
        .x = left.x + right.x,
        .y = left.y + right.y,
    };
}

int main() {
    Point first = MakePoint(239, 1);
    Point second{1, 2};
    Point sum = Add(first, second);

    std::cout << sum.x << ' ' << sum.y << '\n';

    return 0;
}
```

Функция `MakePoint` — простой конструктор-обёртка: принимает два числа и собирает из них объект `Point`. Функция `Add` принимает две точки *по значению* (то есть получает собственные копии `left` и `right`) и возвращает новую точку, поля которой — покомпонентная сумма полей аргументов.

:::note
При передаче по значению крупные объекты копируются целиком, что может быть накладно. Существует способ передавать такие объекты без копирования — по константной ссылке. Этот механизм разбирается отдельно, когда изучаются ссылки.
:::

### Массивы структур

Структуры можно хранить в массивах точно так же, как встроенные типы:

```cpp
#include <string>

struct Record {
    std::string name;
    std::string surname;
    long phone;
};

Record phonebook[200]{};
```

Каждый из 200 элементов массива `phonebook` — это самостоятельный, независимый объект типа `Record` со своим собственным набором полей `name`, `surname` и `phone`. Инициализация `{}` обнуляет («по умолчанию инициализирует») весь массив целиком.

### Указатели на структуры

Если переменная хранит **указатель** на структуру (а не саму структуру), то для доступа к полю через указатель применяется отдельный оператор — стрелка `->`.

:::meaning
Для указателя `pointer` на объект структуры выражения `pointer->field` и `(*pointer).field` **эквивалентны**: оба сначала разыменовывают указатель (получают сам объект), а затем обращаются к его полю. Форма со стрелкой — просто более короткая и читаемая запись того же самого действия.
:::

```cpp
#include <cstddef>

Record* FindRecord(long phone, Record* records, std::size_t count) {
    for (std::size_t index = 0; index < count; ++index) {
        if (records[index].phone == phone) {
            return &records[index];
        }
    }

    return nullptr;
}
```

Функция `FindRecord` перебирает массив `records` длиной `count` в поисках записи с заданным номером телефона `phone`. Как только совпадение найдено, функция возвращает **адрес** найденного элемента (`&records[index]`) — то есть указатель на него. Если совпадений нет, возвращается `nullptr` — признак того, что запись не найдена.

Использование результата:

```cpp
#include <iostream>

Record* record = FindRecord(22345, phonebook, 200);

if (record != nullptr) {
    std::cout << record->name << ' ' << record->surname << '\n';
}
```

Здесь обязательно проверяется, что `record` не равен `nullptr`, прежде чем обращаться к его полям через `->`. Обращение к полю по нулевому указателю — ошибка, которую нужно исключать заранее.

:::warning
Указатель на элемент массива остаётся действительным только до тех пор, пока существует сам массив, и **только пока элемент не был перемещён или удалён**. Например, если бы `phonebook` вышел из области видимости (был уничтожен) или если бы элементы массива переставлялись местами, ранее сохранённый указатель `record` мог бы указывать на «мёртвую» память или не на ту запись, которая ожидается. Это частый источник ошибок при работе с указателями на элементы контейнеров.
:::

## 3. Размещение структур в памяти и выравнивание

### Размещение структуры в памяти

До сих пор структура рассматривалась только как логическое объединение полей. Но у неё есть и физическое представление в памяти, которое важно понимать для написания эффективного кода.

```cpp
#include <cstddef>
#include <cstdint>
#include <cstdio>

struct PoorLayout {
    char a;
    std::int64_t b;
    char c;
};

struct CompactLayout {
    std::int64_t b;
    char a;
    char c;
};

int main() {
    std::printf("           size align offset(b)\n");
    std::printf("Poor:      %zu   %zu     %zu\n",
        sizeof(PoorLayout), alignof(PoorLayout), offsetof(PoorLayout, b));
    std::printf("Compact:   %zu   %zu     %zu\n",
        sizeof(CompactLayout), alignof(CompactLayout), offsetof(CompactLayout, b));
}
```

Обе структуры содержат один и тот же набор полей — `char a`, `std::int64_t b`, `char c`, — но объявлены в разном порядке. На платформе, где `sizeof(std::int64_t) == 8` и `alignof(std::int64_t) == 8`, типичный вывод программы будет таким:

| Структура | Размер (size) | Выравнивание (align) | Смещение поля `b` (offset) |
|---|---|---|---|
| `PoorLayout` | 24 байта | 8 | 8 |
| `CompactLayout` | 16 байт | 8 | 0 |

Несмотря на одинаковый набор полей, размер структур различается на 8 байт! Разберёмся, почему так происходит.

:::meaning
**Выравнивание** (`alignof(T)`) задаёт, каким адресам разрешено соответствовать началу объекта типа `T` для корректного и эффективного доступа к нему. Если `alignof(T) == 8`, то адрес любого объекта типа `T` должен быть кратен 8 (то есть делиться на 8 без остатка). Выравнивание **не следует путать с размером** типа — это разные, хотя и связанные, характеристики: они не обязаны совпадать.
:::

:::meaning
**Padding** («выравнивающие байты», «набивка») — промежутки внутри структуры, которые компилятор добавляет между полями (или в конце структуры), чтобы каждое поле оказалось расположено по адресу, удовлетворяющему требованиям его выравнивания. Эти байты не хранят значение ни одного из полей структуры.
:::

Рассмотрим `PoorLayout` подробнее. Поле `a` (тип `char`, размер и выравнивание — 1 байт) занимает смещение 0. Следующее поле — `b` (тип `std::int64_t`, выравнивание 8) — должно начинаться с адреса, кратного 8. Если бы `b` шло сразу за `a` (то есть со смещения 1), это требование было бы нарушено. Поэтому компилятор вставляет между `a` и `b` **7 байт padding**, чтобы `b` начиналось со смещения 8 — как и показывает `offsetof(PoorLayout, b)` в таблице выше.

После поля `b` (занимающего смещения 8–15) идёт `char c` на смещении 16. Далее необходим ещё один, **завершающий** padding — уже не между полями, а в конце структуры:

:::warning
Без завершающего padding второй элемент массива структур `PoorLayout[2]` начинался бы со смещения 17 (сразу после `c`), а его поле `b` оказалось бы на смещении 25 — то есть **не кратном 8**. Это нарушило бы выравнивание `b` во втором элементе массива. Поэтому компилятор округляет размер всей структуры так, чтобы он был кратен наибольшему выравниванию среди полей (в данном случае 8): вместо 17 байт получается 24. Благодаря этому у второго элемента массива смещения полей будут 24 (начало структуры) и 32 (поле `b`) — оба кратны 8. Здесь предполагается, что и начало самого массива выровнено по 8.
:::

Именно из-за этих двух видов padding (внутреннего — между `a` и `b`, и завершающего — после `c`) размер `PoorLayout` составляет 24 байта, а не 10 (1 + 8 + 1), которые можно было бы наивно ожидать, просто сложив размеры полей.

`CompactLayout` содержит те же поля, но в другом порядке: сначала `b` (выравнивание 8), затем `a` и `c` (по 1 байту каждый). Поле `b` уже стоит первым, поэтому оно автоматически оказывается на смещении 0 — кратном 8, без всякого padding. Поля `a` и `c` занимают смещения 8 и 9 и не требуют выравнивания больше 1 байта. Итоговый размер округляется до кратного 8, то есть до 16 байт (8 байт под `b`, 2 байта под `a` и `c`, и 6 байт завершающего padding).

:::remember
**Перестановка полей структуры может сократить объём padding и, соответственно, размер структуры.** Общее практическое правило — располагать поля от самых «широких» (с наибольшим выравниванием) к самым «узким», чтобы избежать лишних промежутков между ними.
:::

:::note
Всё описанное выше — это правило размещения объектов, определяемое реализацией компилятора и ABI (двоичным интерфейсом приложений) конкретной платформы, а не гарантия того, что любой невыровненный доступ на любом процессоре обязательно будет медленнее. На разных платформах конкретные требования к выравниванию и его последствия могут отличаться.
:::

### Уплотнение

Иногда экономия памяти важнее скорости доступа к полям — например, при хранении огромных массивов небольших структур. Для принудительного отключения padding используется директива `#pragma pack`:

```cpp
#include <cstddef>
#include <cstdint>
#include <iostream>

struct Data {
    char tag;
    std::int32_t value;
};

#pragma pack(push, 1)
struct PackedData {
    char tag;
    std::int32_t value;
};
#pragma pack(pop)

int main() {
    std::cout << "type: size alignment value-offset\n";
    std::cout << "Data: " << sizeof(Data) << ' ' << alignof(Data)
              << ' ' << offsetof(Data, value) << '\n';
    std::cout << "PackedData: " << sizeof(PackedData)
              << ' ' << alignof(PackedData)
              << ' ' << offsetof(PackedData, value) << '\n';
}
```

Типичный вывод:

```
type: size alignment value-offset
Data: 8 4 4
PackedData: 5 1 1
```

В обычной структуре `Data` поле `tag` (`char`) занимает 1 байт, затем 3 байта padding, а поле `value` (`std::int32_t`, выравнивание 4) начинается со смещения 4. Итоговый размер — 8 байт. Директива `#pragma pack(push, 1)` перед `PackedData` указывает компилятору использовать выравнивание в 1 байт для всех полей структуры — это убирает всякий padding: поле `value` теперь начинается сразу после `tag`, со смещения 1, а размер всей структуры — ровно 5 байт (1 + 4).

:::warning
`#pragma pack` — это **расширение конкретного компилятора**, а не часть стандарта C++. При уплотнении структуры её многобайтовые поля (как `value` в `PackedData`) могут оказаться расположены по адресам, не кратным их естественному выравниванию, то есть стать **невыровненными**. Кроме того, при работе с уплотнёнными структурами в бинарных форматах данных (например, при чтении файлов или сетевых пакетов) также необходимо отдельно учитывать порядок байтов (endianness) платформы.
:::

### Меньше памяти — медленнее обработка?

Уплотнение с `#pragma pack(1)` уменьшает размер структуры (в рассмотренном примере — с 8 до 5 байт), но делает поле `value` потенциально невыровненным. Возникает вопрос: не станет ли из-за этого работа с данными медленнее? Чтобы ответить на него, сравним скорость суммирования поля `value` для массива обычных структур `Data` и массива уплотнённых структур `PackedData`.

```cpp
// packing-benchmark-types.h
#pragma once
#include <cstdint>

struct Data {
    char tag;
    std::int32_t value;
};

#pragma pack(push, 1)
struct PackedData {
    char tag;
    std::int32_t value;
};
#pragma pack(pop)
```

При 4096 элементах массив обычных структур `Data` займёт 32 КиБ, а массив уплотнённых `PackedData` — 20 КиБ. Значения в обоих случаях одинаковые — сравнивается именно **время вычисления одной и той же суммы**, а не корректность результата.

### Выравнивание: сравниваем скорость

Для измерения используется библиотека Google Benchmark. Первый бенчмарк суммирует поля `value` обычной (невыровненной проблемой не страдающей) структуры `Data`:

```cpp
// packing-benchmark.cpp
#include "packing-benchmark-types.h"
#include <benchmark/benchmark.h>
#include <vector>

static void SumRegular(benchmark::State& state) {
    std::vector<Data> data(4096, {'A', 1});
    benchmark::DoNotOptimize(data.data());
    for (auto _ : state) {
        benchmark::ClobberMemory();
        std::int64_t sum = 0;
        for (const auto& item : data) {
            sum += item.value;
        }
        benchmark::DoNotOptimize(sum);
    }
}
BENCHMARK(SumRegular);
BENCHMARK_MAIN();
```

Второй бенчмарк выполняет ту же операцию над массивом уплотнённых структур `PackedData`:

```cpp
// packed-sum-benchmark.cpp
#include "packing-benchmark-types.h"
#include <benchmark/benchmark.h>
#include <vector>

static void SumPacked(benchmark::State& state) {
    std::vector<PackedData> data(4096, {'A', 1});
    benchmark::DoNotOptimize(data.data());
    for (auto _ : state) {
        benchmark::ClobberMemory();
        std::int64_t sum = 0;
        for (const auto& item : data) {
            sum += item.value;
        }
        benchmark::DoNotOptimize(sum);
    }
}
BENCHMARK(SumPacked);
BENCHMARK_MAIN();
```

*Запустить оба бенчмарка можно на Quick Bench — сервисе, позволяющем запускать Google Benchmark прямо в браузере. Ссылка на бенчмарк содержит оба теста и определение типов в одном файле; сборка выполняется с параметрами GCC 13.2, стандарт C++23, флаг оптимизации `-O3`.*

Оба теста суммируют одинаковые 4096 значений — единственное отличие между ними в том, *как* эти значения размещены в памяти. Создание и заполнение массива данными вынесено за пределы измеряемого цикла (`for (auto _ : state)`), чтобы измерялось только время суммирования, а не время построения массива.

:::meaning
**Кеш-линия** — блок данных фиксированного размера, которым процессор оперирует при обращении к кешу (загружает и выгружает данные из основной памяти в кеш не побайтово, а целыми такими блоками).
:::

:::note
`benchmark::DoNotOptimize` сообщает оптимизатору компилятора, что переданное значение (адрес массива, итоговую сумму) действительно используется — это не даёт компилятору «оптимизировать» вычисление, попросту выбросив его как бесполезное. `benchmark::ClobberMemory` не позволяет компилятору считать содержимое памяти неизменным между итерациями измерительного цикла, вынуждая перечитывать данные каждый раз заново, как это происходило бы в реальном сценарии использования.
:::

Почему уплотнённые данные *могут* обрабатываться медленнее: невыровненное поле `value` может пересечь границу кеш-линии, и тогда процессору придётся прочитать части одного значения сразу из двух разных кеш-линий, что дороже одного обращения. Однако уплотнение одновременно **экономит место в кеше** — массив `PackedData` занимает меньше памяти (20 КиБ против 32 КиБ) и лучше в него помещается. Поэтому замедление от невыровненного доступа **не гарантировано**: итоговый результат зависит от конкретного процессора и параметров сборки, и эксперимент измеряет суммарный эффект от нескольких одновременно действующих факторов — выравнивания, плотности данных и возможных различий в векторизации кода компилятором.

### alignas: зачем увеличивать выравнивание

Иногда, наоборот, требуется не уменьшить, а **увеличить** выравнивание объекта сверх того, что задаётся по умолчанию для его типа. Для этого служит спецификатор `alignas`:

```cpp
#include <cstdint>
#include <iostream>

struct Data {
    std::int32_t value;
};

struct alignas(64) AlignedData {
    std::int32_t value;
};

int main() {
    AlignedData items[2]{};
    std::cout << "Data: " << sizeof(Data) << ' ' << alignof(Data) << '\n';
    std::cout << "AlignedData: " << sizeof(AlignedData)
              << ' ' << alignof(AlignedData) << '\n';
    std::cout << "array size: " << sizeof(items) << '\n';
    for (const AlignedData& item : items) {
        auto address = reinterpret_cast<std::uintptr_t>(&item);
        std::cout << "address % 64: " << address % 64 << '\n';
    }
}
```

Типичный вывод:

```
Data: 4 4
AlignedData: 64 64
array size: 128
address % 64: 0
address % 64: 0
```

`struct Data` без указаний по выравниванию занимает 4 байта с выравниванием 4 (как обычный `std::int32_t`). А вот `alignas(64)` заставляет каждый объект `AlignedData` занимать 64 байта и располагаться по адресу, кратному 64 — размер структуры увеличивается с 4 байт (полезных данных) до 64 (за счёт добавленного padding). Как следствие, для обоих элементов массива `items` вывод показывает $\text{address} \bmod 64 = 0$: адреса действительно кратны 64.

:::formula
$$
\text{address} \bmod 64 = 0
$$
Это условие означает, что адрес объекта делится на 64 без остатка — то есть объект начинается ровно на границе 64-байтового блока памяти.
:::

Цена такого выравнивания велика: 64 байта памяти вместо 4 полезных. Так зачем это может понадобиться?

:::meaning
**False sharing** («ложное совместное использование») — ситуация, при которой два независимых объекта, изменяемых *разными* потоками, случайно попадают в одну и ту же кеш-линию. Поскольку протокол согласования кешей процессора работает с целыми кеш-линиями, а не с отдельными байтами внутри них, изменение одного объекта одним потоком вынуждает инвалидировать всю кеш-линию (в том числе и для другого объекта) в кеше другого ядра — даже если второй поток вообще не трогал первый объект.
:::

Идея `alignas(64)` — разнести данные, которые часто и независимо изменяются разными потоками, по разным кеш-линиям, чтобы избежать false sharing. Если размер кеш-линии равен 64 байтам, то `alignas(64)` гарантирует, что элементы массива `items` попадут каждый в свою собственную кеш-линию и не будут «мешать» друг другу при параллельном изменении разными ядрами процессора.

:::note
Без увеличенного выравнивания соседние четырёхбайтовые объекты `Data` вполне могут оказаться в одной кеш-линии. Когда разные ядра меняют каждое свой отдельный объект, протокол согласования кешей всё равно будет обрабатывать это как конфликт над целой линией, порождая лишние — по сути ненужные — взаимодействия между ядрами.
:::

Как выбрать нужное значение выравнивания на практике? Начиная с C++17, в заголовке `<new>` определена константа `std::hardware_destructive_interference_size` — рекомендуемое реализацией расстояние между независимо изменяемыми объектами, помогающее избежать false sharing. Значение `64`, использованное в примере выше, — это выбор, подходящий для конкретной рассматриваемой платформы, а не универсальная константа языка.

:::warning
Значение `std::hardware_destructive_interference_size` определяется реализацией **во время компиляции**, а не измеряется во время выполнения программы. Если конкретная библиотека не предоставляет эту константу (это можно проверить макросом `__cpp_lib_hardware_interference_size`), выравнивание приходится подбирать вручную, ориентируясь на целевую платформу.
:::

Ещё одна причина увеличивать выравнивание — требования отдельных **SIMD-инструкций** процессора, которые обрабатывают сразу несколько чисел за одну инструкцию: такие инструкции часто требуют, чтобы данные были выровнены по определённой границе, и конкретное требуемое значение зависит от используемой инструкции.

:::note
В данном разделе рассматривается только размещение данных в памяти — сам пример *не* является многопоточным бенчмарком, измеряющим реальный выигрыш от устранения false sharing. Размер кеш-линии зависит от конкретной платформы; 64 байта в примере — это условие, выбранное для иллюстрации, а не гарантия, зафиксированная в языке. Само по себе увеличение выравнивания не гарантирует ускорения программы и всегда повышает расход памяти — это осознанный компромисс, который стоит применять только тогда, когда false sharing (или требования конкретной SIMD-инструкции) действительно являются проблемой.
:::

## 4. Объединения

:::meaning
**Объединение** (`union`) — пользовательский тип, у которого **все поля используют одну и ту же область памяти**. В каждый момент времени осмысленно («активно») только одно из полей объединения — то, которое было записано последним.
:::

```cpp
// union-definition.h
#pragma once
#include <cstdint>

union Value {
    std::int64_t integer;
    double real;
    char text[16];
};
```

В отличие от структуры, где каждое поле занимает *своё* место в памяти (и потому размер структуры примерно равен сумме размеров её полей, плюс padding), у объединения поля `integer`, `real` и `text` начинаются **с одного и того же адреса** и физически делят общую область памяти. Размер `union Value` достаточен для размещения самого крупного из полей (с учётом требований выравнивания) — то есть не суммируется, как у структуры, а берётся по максимуму.

### Активное поле объединения

```cpp
// union-value.cpp
#include "union-definition.h"
#include <iostream>

int main() {
    Value value{};
    std::cout << sizeof(value) << '\n';

    value.integer = 239;
    std::cout << value.integer << '\n';  // активен integer

    value.real = 3.14;
    std::cout << value.real << '\n';  // теперь активен real

    return 0;
}
```

После `value.integer = 239;` активным полем объединения становится `integer`, и его можно безопасно читать. Но как только выполняется `value.real = 3.14;`, это **перезаписывает** ту же самую область памяти как значение типа `double` — и активным становится уже поле `real`. С этого момента поле `integer` больше не хранит осмысленного значения `239`: та же память теперь интерпретируется как `double`.

:::warning
Чтение **неактивного** поля обычного `union` в общем случае приводит к **неопределённому поведению (UB)** в стандартном C++. `union` — это инструмент совместного хранения *альтернативных* объектов (в каждый момент времени по смыслу существует только один из них), а не переносимый способ преобразовывать битовое представление данных между несвязанными типами.
:::

Для безопасного копирования битового представления одного типа в другой применяется функция `std::memcpy`, а для типов одинакового размера начиная с C++20 доступен более безопасный и явный инструмент — `std::bit_cast`.

### Tagged union: данные и тег

Объединения удобны для хранения «одно из нескольких» значений разных типов, но сами по себе они не запоминают, какое поле активно в данный момент — это должен отслеживать сам программист. Стандартный приём для этого — **tagged union** («размеченное объединение»): объединение хранится вместе с отдельной переменной-«тегом», которая указывает, какое из полей объединения сейчас активно.

Начнём с описания самих типов фигур:

```cpp
// figure-shapes.h
#pragma once

struct Point {
    float x;
    float y;
};

struct Triangle {
    Point a;
    Point b;
    Point c;
};

struct Rectangle {
    Point left_top;
    Point right_bottom;
};

struct Circle {
    Point center;
    float radius;
};
```

Теперь добавим тег и само объединение:

```cpp
// tagged-figure.h
#pragma once
#include "figure-shapes.h"

enum class FigureType {
    Triangle,
    Rectangle,
    Circle,
};

union FigureData {
    Triangle triangle;
    Rectangle rectangle;
    Circle circle;
};

struct Figure {
    FigureType type;
    FigureData data;
};
```

:::meaning
В структуре `Figure` поле `type` — это **тег**, значение которого сообщает, какое из полей объединения `data` в данный момент активно: значению `FigureType::Circle` соответствует активное поле `data.circle`, значению `FigureType::Rectangle` — активное поле `data.rectangle`, и так далее.
:::

Теперь можно хранить массив разнородных фигур как массив объектов одного типа `Figure`:

{% raw %}
```cpp
// tagged-union-use.cpp
#include "tagged-figure.h"
#include <iostream>

int main() {
    Figure figures[]{
        {FigureType::Circle, {.circle = {{0, 0}, 10}}},
        {FigureType::Rectangle, {.rectangle = {{0, 10}, {20, 0}}}},
        {FigureType::Triangle, {.triangle = {{0, 0}, {4, 0}, {0, 3}}}},
    };

    for (Figure figure : figures) {
        switch (figure.type) {
        case FigureType::Circle:
            std::cout << "Radius: "
                      << figure.data.circle.radius << '\n';
            break;
        case FigureType::Rectangle:
            std::cout << "Left x: "
                      << figure.data.rectangle.left_top.x << '\n';
            break;
        case FigureType::Triangle:
            std::cout << "Vertex A x: "
                      << figure.data.triangle.a.x << '\n';
            break;
        }
    }
}
{% endraw %}


:::example
Разберём пошагово, как здесь используется тег для безопасной работы с объединением.
1. Массив `figures` хранит три элемента типа `Figure`: круг, прямоугольник и треугольник. Каждый элемент — это пара «тег + данные» (`{FigureType::Circle, {.circle = ...}}` и так далее).
2. В цикле `for (Figure figure : figures)` элементы массива копируются по значению в переменную цикла `figure` (ссылки на этом этапе курса ещё не изучались).
3. Оператор `switch (figure.type)` проверяет значение тега и в зависимости от него выполняет соответствующую ветку `case`.
4. В каждой ветке читается **только то поле объединения `data`, которое соответствует текущему значению тега**: например, в ветке `FigureType::Circle` читается `figure.data.circle`, а не `figure.data.rectangle` или `figure.data.triangle`. Именно за счёт этого код не нарушает правило «не читать неактивное поле union»: тег гарантирует, что читается ровно то поле, которое было записано.
5. Геометрические данные вариантов, не совпадающих с текущим тегом, в цикле вообще не читаются.
:::

:::warning
Тег и активное поле объединения — это две **независимые** переменные, синхронизацию между которыми обеспечивает исключительно программист. Изменение одного тега само по себе **не переключает** активное поле объединения — программе приходится вручную поддерживать их согласованность (то есть одновременно менять и тег, и записывать соответствующее поле).
:::

Размеры полей на схемах в примерах приведены для платформы, где `sizeof(float) == 4` байта.

### std::variant

Работа с tagged union вручную требует дисциплины: легко забыть обновить тег или случайно прочитать не то поле. В современном C++ более безопасной альтернативой ручному tagged union служит `std::variant`:

```cpp
#include <variant>

using Figure = std::variant<Triangle, Rectangle, Circle>;

Figure figure = Circle{
    .center = {0.0F, 0.0F},
    .radius = 10.0F,
};
```

:::remember
`std::variant` самостоятельно хранит тег внутри себя и контролирует время жизни активного объекта — программисту больше не нужно вручную заводить отдельный `enum` с тегом и объединение. Для безопасной работы с содержимым `std::variant` используются функции `std::get`, `std::get_if` и `std::visit`.
:::

### Код из 2005 года

Иногда `union` используют не для хранения альтернативных значений, а для намеренного «взгляда» на одни и те же байты через разные наборы полей — приём, называемый **type punning**. Рассмотрим пример, характерный для более старого стиля C++:

```cpp
// name-comparison.h
#pragma once
#include <cstdint>
#include <cstring>

union Name {
    struct {
        char name[13];
        char code[3];
    } text;
    struct {
        std::int32_t i1, i2, i3, i4;
    } words;
};

static_assert(sizeof(Name) == 16);

inline bool NameCompare(const Name& a, const Name& b) {
    return std::strcmp(a.text.name, b.text.name) == 0
        && std::strcmp(a.text.code, b.text.code) == 0;
}

// Чтение неактивного члена union: расширение компилятора, UB в ISO C++.
inline bool IntCompare(const Name& a, const Name& b) {
    return a.words.i1 == b.words.i1
        && a.words.i2 == b.words.i2
        && a.words.i3 == b.words.i3
        && a.words.i4 == b.words.i4;
}
```

Здесь `union Name` позволяет смотреть на одни и те же 16 байт двумя способами: как на пару строк (`text.name` и `text.code`) или как на четыре 32-битных целых числа (`words.i1`…`words.i4`). Идея в том, чтобы сравнивать имена двумя разными способами, работая с одними и теми же исходными данными, и сопоставить их скорость.

:::warning
Чтение неактивного поля `union` — неопределённое поведение (UB) в стандартном ISO C++. Функция `IntCompare` записывает значения через `text`, а читает через `words` — то есть читает поле, которое формально не является активным. Приведённый код полагается на **расширение компилятора GCC**, которое разрешает такое чтение (в отличие от строгого стандарта). Эксперимент с этим кодом требует компилятора, поддерживающего данное расширение.
:::

:::note
Сравнение *всех байтов* объекта `Name` эквивалентно сравнению строк (`NameCompare`) только при условии, что заполнение байтов после завершающего нулевого символа `\0` у обеих строк одинаковое. В рассматриваемом примере массивы `name` и `code` заполняются строками целиком, включая завершающий терминатор, поэтому это условие выполняется.
:::

### Google Benchmark: строки и целые числа

Сравним скорость двух функций сравнения — через строки (`NameCompare`) и через целые числа (`IntCompare`) — на одних и тех же входных данных.

Бенчмарк для сравнения строк:

```cpp
// name-comparison-benchmark.cpp
#include "name-comparison.h"
#include <benchmark/benchmark.h>

static void NameComparison(benchmark::State& state) {
    Name a{.text = {"0123456789AB", "12"}};
    Name b{.text = {"0123456789AB", "10"}};

    benchmark::DoNotOptimize(a);
    benchmark::DoNotOptimize(b);
    for (auto _ : state) {
        bool result = NameCompare(a, b);
        benchmark::DoNotOptimize(result);
    }
}
BENCHMARK(NameComparison);
BENCHMARK_MAIN();
```

Бенчмарк для сравнения через целые числа:

```cpp
// integer-comparison-benchmark.cpp
#include "integer-comparison.h"
#include <benchmark/benchmark.h>

static void IntComparison(benchmark::State& state) {
    Name a{.text = {"0123456789AB", "12"}};
    Name b{.text = {"0123456789AB", "10"}};

    benchmark::DoNotOptimize(a);
    benchmark::DoNotOptimize(b);
    for (auto _ : state) {
        bool result = IntCompare(a, b);
        benchmark::DoNotOptimize(result);
    }
}
BENCHMARK(IntComparison);
BENCHMARK_MAIN();
```

*Оба теста запускаются на Quick Bench с одинаковыми входными данными; отличается только функция сравнения. Для запуска нужно выбрать компилятор GCC — только он поддерживает используемое здесь расширение для чтения неактивного члена `union`. Сборка выполняется со стандартом C++20 и флагом оптимизации `-O2`.*

:::note
`benchmark::DoNotOptimize` не даёт компилятору посчитать переданное значение неиспользуемым и удалить связанные с ним вычисления. Для сборки бенчмарков требуется библиотека Google Benchmark; заголовочные файлы примера должны лежать рядом с `.cpp`-файлами. В правом (втором) тесте читается неактивный член `union` — в терминах ISO C++ это неопределённое поведение, и эксперимент опирается на расширение конкретного компилятора.
:::

### Результаты в Quick Bench

Quick Bench — это сервис, позволяющий запускать бенчмарки, написанные с помощью Google Benchmark, прямо в браузере, без локальной настройки окружения сборки.

:::remember
В исходном эксперименте сравнение четырёх целых чисел (`IntCompare`) оказалось существенно быстрее, чем два последовательных вызова `strcmp` (`NameCompare`). Сравнение целых чисел — это несколько простых машинных операций сравнения, тогда как `strcmp` должен последовательно, байт за байтом, искать завершающий нулевой символ в каждой из строк, что требует больше работы на тех же данных.
:::

:::note
Конкретная величина выигрыша в скорости зависит от входных данных, используемого компилятора и целевой платформы. Кроме того, стоит помнить, что сам пример с `IntCompare` полагается на расширение компилятора (чтение неактивного члена `union`) и не является переносимым между всеми компиляторами и платформами способом type punning.
:::
