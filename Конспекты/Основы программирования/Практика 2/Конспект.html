Основы программирования

CMake и сборка многофайлового C++-проекта

Конспект объясняет один процесс в двух формах: сначала сборку нескольких файлов командой clang++, затем описание той же сборки в CMake. Все примеры используют clang++.

Обозначения: <имя> — значение пользователя; [X] — необязательная часть; A | B — один вариант; ... — повторение. Аргументы CMake разделяются пробелами.

1. Что происходит при сборке C++

Определение

Единица трансляции — результат обработки одного файла .cpp препроцессором. В этот результат уже подставлены все подключённые заголовки, раскрыты макросы и выбраны ветви условной компиляции. Компилятор обрабатывает именно единицы трансляции, а не весь проект одновременно.

Процессор исполняет машинные инструкции, а не текст C++. Поэтому команда clang++ выполняет цепочку преобразований. Первые три стадии обрабатывают каждый .cpp отдельно. Последняя стадия соединяет их результаты в одну программу.

bash / PowerShell
clang++ main.cpp -o app
1. Препроцессингобрабатывает #include и макросы
2. Компиляцияпроверяет C++ и создаёт ассемблер
3. Ассемблированиесоздаёт объектный файл .o/.obj
4. Линковкасвязывает объектные файлы и библиотеки
Следствие

Компилятор может проверить вызов функции, если видит её объявление. Однако адрес функции он узнаёт только на этапе линковки, когда получит объектный файл с её определением. Из этого следуют две темы следующего раздела: заголовки содержат объявления, а линковщик соединяет реализации из разных .cpp-файлов.

1.1 Препроцессор: текст до C++

Препроцессор обрабатывает директивы, начинающиеся с #. Он не проверяет типы и не различает функции, классы и переменные: для него это текст. Директива #include заменяется содержимым указанного файла. Поэтому заголовок становится частью текущей единицы трансляции до начала проверки C++-кода.

Макросы в C++

Макросы в C++ — это инструкции для препроцессора, которые заменяются на текст ещё до начала компиляции программы.

ДирективаТочное действиеКогда используется
#include "file.h"Препроцессор находит файл и подставляет его содержимое вместо строки #include. При такой форме Clang сначала ищет файл рядом с тем файлом, где написан #include, затем — в каталогах, переданных через -I, и стандартных путях поиска.Заголовки текущего проекта: "lib.hpp", "test.hpp".
#include <vector>Также подставляет содержимое заголовка, но ищет его в путях для системных и подключённых библиотек. Каталог текущего исходного файла не является первым местом поиска.Стандартные заголовки C++: <vector>, <iostream>, <fstream>; заголовки внешних библиотек.
#define NAME valueСоздаёт макрос: правило замены последовательности токенов NAME на value в последующем тексте единицы трансляции. Замена выполняется до разбора C++.Константа или переключатель для препроцессора. Макрос не имеет типа C++ и не проходит проверку типов.
#if, #ifdefВычисляет условие во время препроцессинга и оставляет в результате только одну ветку. Отброшенная ветка не передаётся компилятору.Код, который зависит от заданного макроса: платформа, отладочный режим или включённая возможность.
Макрос: исходный текст и результат подстановки
#define BUFFER_SIZE 128

int values[BUFFER_SIZE];

// После препроцессинга:
int values[128];

В этом примере препроцессор не знает, что 128 — размер массива и что values — массив. Он заменяет токен BUFFER_SIZE на токен 128, а затем компилятор проверяет уже получившуюся строку. Поэтому макрос не заменяет константу C++: у constexpr int buffer_size = 128; есть тип и область видимости, а у макроса их нет.

Условная компиляция для разных платформ
#ifdef _WIN32
constexpr char path_separator = '\\';
#else
constexpr char path_separator = '/';
#endif

Макрос _WIN32 определяет компилятор при сборке программы для Windows. При такой сборке препроцессор оставит только первую строку с path_separator; при сборке для Linux или macOS — только вторую. Компилятор никогда не увидит отброшенную ветку, поэтому в ней может находиться код, подходящий только другой платформе.

Например, если в main.cpp написано #include "lib.hpp", а в lib.hpp находится объявление void Hello();, то после препроцессинга в том месте, где была директива, окажется текст объявления. Компилятор затем видит не саму директиву, а обычный C++-текст с объявлением функции.

Результат #include на небольшом примере
// Содержимое lib.hpp
void Hello();

// Содержимое main.cpp до препроцессинга
#include "lib.hpp"

int main() {
    Hello();
}

// Главная часть main.cpp после препроцессинга
void Hello();

int main() {
    Hello();
}

Флаг -E просит clang++ выполнить только препроцессинг и остановиться. В частности, компилятор не проверяет типы, не создаёт объектный файл и не запускает линковщик. Результат обычно записывают в файл с расширением .i; это соглашение об имени, а не специальный формат.

bash / PowerShell
clang++ -E main.cpp -o main.i

Файл main.i предназначен для просмотра, а не для редактирования. В нём могут оказаться тысячи строк из стандартных заголовков и служебные строки с номерами исходных файлов. Если нужны только развёрнутые директивы без таких строк, к команде добавляют -P: clang++ -E -P main.cpp -o main.i. Этот способ применяют, когда нужно понять, какой именно текст получил компилятор: например, почему имя объявлено дважды или почему условная ветка не попала в сборку.

Почему не подключают .cpp

#include не добавляет файл в проект и не говорит компилятору «скомпилируй этот файл отдельно». Он буквально вставляет содержимое файла в текущую единицу трансляции. Поэтому после #include "lib.cpp" тело Hello() становится частью main.cpp.

Само по себе такое включение не всегда вызывает ошибку: если lib.cpp больше нигде не компилируется, программа может собраться как одна большая единица трансляции. Однако это не организация обычного многофайлового проекта. Ошибка duplicate symbol возникает в типичной ситуации, когда main.cpp включает lib.cpp, а команда одновременно передаёт lib.cpp компилятору отдельно: clang++ main.cpp lib.cpp -o app. Тогда определение Hello() попадает в программу дважды. Заголовки подключают через #include, а каждый .cpp перечисляют отдельным аргументом clang++ или в add_library/add_executable.

1.2 Компиляция, ассемблирование и объектный файл

После препроцессинга компилятор проверяет синтаксис, типы и правила видимости имён. Затем он создаёт ассемблерный код, а ассемблер — объектный файл. При обычной сборке эти действия скрыты внутри clang++. Флаг -c означает: выполнить преобразование до объектного файла и не запускать линковщик.

Linux / macOS
clang++ -std=c++20 -c main.cpp -o main.o
Windows PowerShell
clang++ -std=c++20 -c main.cpp -o main.obj

Файл main.o на Linux/macOS или main.obj на Windows содержит машинный код одной единицы трансляции и таблицу символов. Таблица сообщает, какие символы этот файл определяет и какие символы ему требуются извне. Поэтому в main.o может быть ссылка на print_greeting() без её адреса: адрес будет найден при линковке.

2. Заголовок, объявление и определение

Рассмотрим вызов Hello() из main.cpp. При компиляции main.cpp компилятор не открывает lib.cpp сам. Он должен получить описание функции из текста main.cpp и подключённых заголовков. Поэтому интерфейс функции и её реализация разделяются.

ПонятиеПримерЧто сообщает компилятору
Объявлениеvoid print_greeting();Имя и тип функции.
Определениеvoid print_greeting() { ... }Тело функции.

Объявление отвечает на вопрос «как эту сущность использовать»: у функции известны имя, тип результата и параметры. Определение отвечает на вопрос «какой код будет выполнен»: оно содержит тело функции. Объявление можно повторять в разных единицах трансляции. Обычная функция с внешним связыванием должна иметь одно определение в программе. Это правило единственного определения.

2.1 Линейный проект

project/ ├── main.cpp ├── lib.cpp ├── lib.hpp ├── test.cpp └── test.hpp
main.cpp
#include "lib.hpp"
#include "test.hpp"

#include <iostream>

int main() {
    Hello();
    std::cout << '\n';
    Test();
}
Linux / macOS
clang++ main.cpp test.cpp lib.cpp -o main
./main
Windows PowerShell
clang++ main.cpp test.cpp lib.cpp -o main
.\main.exe

Здесь все файлы находятся в одной директории. Для формы #include "lib.hpp" Clang сначала ищет файл рядом с тем файлом, который выполняет включение. Поэтому -I не нужен. Если бы lib.hpp лежал в отдельной директории, этот каталог пришлось бы передать через -I.

Команда содержит три исходных файла. Clang создаёт одну единицу трансляции для main.cpp, одну для test.cpp и одну для lib.cpp; затем линковщик объединяет результаты. В main.cpp подключаются только lib.hpp и test.hpp, то есть объявления. Записи #include "lib.cpp" и #include "test.cpp" здесь быть не должно: реализации уже переданы компилятору отдельными аргументами.

  1. main.cpp получает объявления Hello() и Test() из заголовков.
  2. test.cpp подключает lib.hpp, потому что внутри Test() вызывается Hello().
  3. lib.cpp определяет Hello(); test.cpp определяет Test().
  4. Линковщик связывает вызовы из main.cpp и test.cpp с этими определениями.
project/ ├── bin/ │ └── main.cpp └── lib/ ├── greeting.h └── greeting.cpp
lib/greeting.h — интерфейс
#ifndef GREETING_H
#define GREETING_H

void print_greeting();

#endif  // GREETING_H
lib/greeting.cpp — реализация
#include "greeting.h"

#include <iostream>

void print_greeting() {
    std::cout << "Hello\n";
}
bin/main.cpp — использование
#include "greeting.h"

int main() {
    print_greeting();
}

2.2 Проект с каталогами

В следующем варианте приложение и библиотека разнесены по каталогам. Такое разделение не меняет правила C++, но меняет пути поиска заголовков. Заголовок greeting.h по-прежнему содержит объявление, а greeting.cpp — определение.

  1. greeting.h подставляется в main.cpp. Поэтому компилятор знает, что вызов print_greeting() допустим и не требует параметров.
  2. greeting.h подставляется в greeting.cpp. Если определение будет иметь другой тип результата или параметры, ошибка появится при компиляции greeting.cpp.
  3. Компиляция greeting.cpp создаёт greeting.o или greeting.obj с определением символа print_greeting.
  4. Компиляция main.cpp создаёт объектный файл со ссылкой на этот символ.
  5. Линковщик сопоставляет ссылку из main.o с определением из greeting.o.

2.3 Защита от повторного включения

Защита от повторного включения — механизм, который не позволяет препроцессору вставить один и тот же заголовок дважды в одну единицу трансляции. Она нужна потому, что заголовок может быть подключён несколькими путями. Например, main.cpp подключает a.hpp, а a.hpp подключает greeting.h; при этом main.cpp может подключать greeting.h и напрямую. Без защиты текст greeting.h оказался бы в результате препроцессинга дважды.

  1. При первом включении макрос GREETING_H ещё не определён, поэтому текст между #ifndef и #endif подставляется.
  2. #define GREETING_H определяет макрос до следующего включения этого же заголовка.
  3. При следующем включении условие #ifndef GREETING_H ложно. Препроцессор пропускает весь блок.

Такой шаблон из #ifndef, #define и #endif называют include guard. Имя GREETING_H является обычным макросом; его выбирают так, чтобы оно было уникально для заголовка. Если два независимых заголовка используют один и тот же макрос, один из них может быть ошибочно пропущен. Поэтому в больших проектах в имя включают каталог или название библиотеки, например PRACTICE_LIB_GREETING_HPP.

#pragma once — другая форма той же защиты. Эту строку помещают первой в заголовок. Она означает: «данный физический файл разрешено включить не более одного раза в каждую единицу трансляции». Это не часть стандарта C++, но поддерживается Clang, GCC и MSVC. Include guard использует только стандартные директивы препроцессора, поэтому его действие определено независимо от конкретного компилятора.

Граница действия защиты

Include guard и #pragma once защищают только заголовок и только внутри одной единицы трансляции. Они не запрещают компилировать один .cpp-файл дважды и не исправляют ошибку в команде сборки. Если greeting.cpp попал в две разные цели либо был передан clang++ дважды, линковщик всё равно увидит два определения print_greeting() и выдаст multiple definition или duplicate symbol.

Угловые скобки и кавычки задают порядок поиска файла, а не видимость имён в C++. Для заголовка своего проекта используют кавычки; для стандартной библиотеки — угловые скобки. Это соглашение делает происхождение заголовка понятным при чтении кода.

3. Линковка: символы и два класса ошибок

Определение

Линковщик — программа, которая получает объектные файлы и библиотеки после компиляции. Она сопоставляет каждое внешнее обращение к функции или переменной с единственным подходящим определением и создаёт исполняемый файл либо библиотеку.

Для линковщика функция или глобальная переменная представлена символом. Символ — это имя сущности в объектном файле вместе со сведениями, необходимыми для её связывания. Например, после компиляции main.cpp объектный файл содержит запись: «в программе требуется функция print_greeting()». После компиляции greeting.cpp другой объектный файл содержит запись: «здесь находится реализация print_greeting()».

  1. Компилятор main.cpp проверяет вызов по объявлению из заголовка, но не знает адрес кода функции.
  2. Компилятор greeting.cpp создаёт машинный код функции и помещает его в свой объектный файл.
  3. Линковщик находит определение во втором объектном файле, подставляет адрес в вызов из первого и завершает программу.

Следовательно, объявление решает задачу проверки исходного кода, а определение решает задачу создания исполняемого кода. Наличие объявления не заменяет передачу реализации линковщику.

СообщениеЭтапПричинаЧто проверить
file not found, use of undeclared identifierКомпиляцияКомпилятор не нашёл заголовок или после обработки заголовков не увидел объявления имени.Правильность #include, регистр имени файла, путь -I, наличие объявления в заголовке.
undefined reference / Undefined symbolsЛинковкаВызов был скомпилирован по объявлению, но объектный файл или библиотека с определением не участвовали в линковке.Добавлен ли нужный .cpp, .o или target-библиотека; совпадают ли объявление и определение.

Различие сообщений

Ошибка компиляции обычно указывает на конкретный файл и строку исходного текста: компилятор ещё разбирает одну единицу трансляции. Ошибка линковки появляется после успешной компиляции файлов и называет отсутствующий или повторно определённый символ. Поэтому при use of undeclared identifier ищут заголовок и объявление, а при undefined reference — реализацию, не попавшую в команду сборки или в зависимость CMake.

4. Ручная сборка

Без CMake разработчик сам описывает все зависимости в командах clang++. Для каждого исходного файла нужно указать, где искать заголовки, какие правила языка применять и в какой объектный файл записать результат. Затем отдельная команда передаёт все объектные файлы линковщику. На небольшом примере это удобно: связь между командами видна напрямую.

Linux и macOS

shell
clang++ -std=c++20 -Ilib -c lib/greeting.cpp -o greeting.o
clang++ -std=c++20 -Ilib -c bin/main.cpp -o main.o
clang++ main.o greeting.o -o app
./app

Windows · PowerShell

PowerShell
clang++ -std=c++20 -Ilib -c lib/greeting.cpp -o greeting.obj
clang++ -std=c++20 -Ilib -c bin/main.cpp -o main.obj
clang++ main.obj greeting.obj -o app.exe
.\app.exe

В первых двух командах флаг -c останавливает работу после создания объектного файла. Флаг -std=c++20 выбирает правила языка C++20. Флаг -Ilib добавляет каталог lib в пути поиска собственных заголовков, поэтому строка #include "greeting.h" в bin/main.cpp становится разрешимой. Последняя команда получает только объектные файлы; без -c clang++ запускает линковку и создаёт итоговую программу.

Если изменить только lib/greeting.cpp, достаточно повторить первую и третью команды: main.o не зависит от текста реализации. Именно такой учёт зависимостей автоматизирует система сборки.

Windows

clang++ должен быть доступен из той консоли, где выполняется команда; также в окружении должны быть средства линковки C++. На Windows обычно используют расширения .obj и .exe. Смысл команд, исходный C++ и порядок этапов остаются теми же, что на Linux и macOS.

5. CMake

CMake — генератор систем сборки, а не компилятор. Он читает файлы CMakeLists.txt, создаёт описание целей и зависимостей, а затем записывает инструкции для конкретного инструмента сборки: Ninja, Make, Visual Studio, Xcode и других. Уже этот инструмент вызывает выбранный компилятор; во всех командах данного конспекта им является clang++.

CMake configureчитает CMakeLists.txt
Generatorсоздаёт Ninja/Make/IDE-файлы
Native build toolпланирует только нужные шаги
clang++ / linkerкомпилирует и линкует
Цель (target)

Цель — именованная единица сборки. У цели есть исходные файлы, зависимости, пути к заголовкам, требуемый стандарт C++ и параметры компиляции. Целью может быть исполняемый файл или библиотека. Запись app → greeting означает, что для сборки app сначала должна быть собрана библиотека greeting.

Цели образуют ориентированный граф зависимостей. Из этой модели следует инкрементальная сборка: если изменён lib/greeting.cpp, система сначала пересобирает объектный файл и библиотеку greeting, а затем выполняет только те действия, которые необходимы для зависящих целей. Файлы, чьи исходники и настройки не изменились, повторно не компилируются.

5.1 Исходное дерево и дерево сборки

Исходное дерево — каталог, который создаёт и изменяет разработчик. В нём находятся исходные файлы .cpp, заголовки .hpp, файлы CMakeLists.txt, документация и настройки проекта. Этот каталог описывает программу, но не содержит результата её компиляции.

Дерево сборки — отдельный каталог, который создают CMake и выбранная система сборки. В нём находятся файлы с настройками конкретного запуска CMake, объектные файлы, библиотеки и исполняемые файлы. Его содержимое зависит от операционной системы, компилятора, генератора и выбранной конфигурации. Поэтому дерево сборки можно удалить и создать заново из исходного дерева; исходный код при этом не изменяется.

Например, после команды cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=clang++ два дерева существуют рядом, но имеют разные роли:

practice-02/ # исходное дерево ├── CMakeLists.txt ├── bin/ │ └── main.cpp ├── lib/ │ ├── include/ │ └── src/ └── build/ # дерево сборки ├── CMakeCache.txt # сохранённые параметры configure ├── CMakeFiles/ # результаты проверок CMake ├── build.ninja # правила сборки для Ninja ├── bin/practice_02 # программа на Linux/macOS └── lib/libpractice_lib.a # статическая библиотека

Разделение деревьев не является особенностью только CMake. Оно отделяет исходный код от воспроизводимых результатов сборки. Один и тот же исходный каталог можно настроить в нескольких каталогах: например, build-debug для отладки и build-release для оптимизированной программы. Эти каталоги не должны добавляться в систему контроля версий.

Command-line generator + clang++
cmake -S . -B build -G Ninja -DCMAKE_CXX_COMPILER=clang++
cmake --build build --parallel
  1. -S . сообщает CMake, что корневой CMakeLists.txt находится в текущем каталоге.
  2. -B build задаёт отдельный каталог для результатов configure и build. Если его нет, CMake создаёт его.
  3. -G Ninja выбирает генератор Ninja. CMake создаст в build файл build.ninja, а Ninja прочитает его на следующем шаге.
  4. -DCMAKE_CXX_COMPILER=clang++ выбирает компилятор из PATH. Этот параметр следует задать при первом configure нового дерева сборки.
  5. cmake --build build --parallel не запускает C++-компилятор напрямую. CMake передаёт управление генератору, а тот выполняет необходимые команды clang++ параллельно там, где это возможно.
Кэш CMake

Кэш CMake — файл build/CMakeCache.txt, в котором CMake сохраняет значения параметров configure и результаты проверок среды. В частности, там фиксируются выбранный генератор, найденный путь к clang++, пути к библиотекам и пользовательские значения, переданные как -DИМЯ=ЗНАЧЕНИЕ. При следующем запуске CMake читает эти значения, чтобы не определять среду заново.

Выбор генератора и компилятора относится к первичной настройке дерева сборки. Например, если каталог build был создан с Ninja и одним экземпляром Clang, команда с другим генератором в том же каталоге завершится ошибкой. Простая смена CMAKE_CXX_COMPILER в уже созданном кэше также не является корректной заменой компилятора: результаты проверок и правила сборки были получены для прежнего выбора. Для другого генератора или другого компилятора создают новый каталог сборки, например build-clang. Старый каталог можно удалить целиком, если его результаты больше не нужны; исходные файлы от этого не затрагиваются.

6. Синтаксис CMake и переменные

Файл CMakeLists.txt исполняется CMake во время configure. Его строки не являются командами компилятора и не выполняются при запуске готовой программы. Они описывают, какие цели существуют и какими свойствами они обладают. Основная форма языка CMake — вызов команды с именем и списком аргументов:

CMake
command_name(argument1 argument2)
# комментарий начинается с решётки
set(VARIABLE value)
message(STATUS "VARIABLE = ${VARIABLE}")
  • Аргументы разделяются пробелами или переносами строк, не запятыми. Поэтому переносы в длинной команде служат только для читаемости.
  • set(NAME value) создаёт или изменяет переменную CMake в текущей области видимости. Это значение существует во время configure.
  • ${NAME} подставляет значение переменной в аргумент команды. Например, в строке message(STATUS "${NAME}") CMake заменит конструкцию ${NAME} до выполнения message.
  • message(STATUS ...) выводит диагностическое сообщение во время configure. Оно не становится частью программы на C++.
Следствие

Переменная сама по себе не меняет сборку. Строка set(MY_FLAG -Wall) только сохраняет текст -Wall. Чтобы этот флаг получил Clang, значение нужно передать в свойство конкретной цели, например target_compile_options(app PRIVATE ${MY_FLAG}). Тем самым CMake отделяет временные вычисления при configure от настроек реальной сборки.

КомандаНазначениеПримечание
cmake_minimum_required(VERSION 3.25)Устанавливает минимальную версию CMake, с которой совместим проект.Это не версия компилятора и не версия C++.
project(name LANGUAGES CXX)Объявляет проект и включает поддержку языка C++.CXX — имя C++ в терминологии CMake. После этой команды CMake ищет и проверяет компилятор C++.
add_executable(name src...)Создаёт цель исполняемого файла и связывает с ней перечисленные исходники.Команда описывает цель; компиляция произойдёт позже, на шаге build.
add_library(name STATIC src...)Создаёт цель статической библиотеки из перечисленных исходников.STATIC задан явно, поэтому вид результата не зависит от платформенной настройки по умолчанию.

7. Структура проекта

Ниже приведена минимальная структура, в которой приложение отделено от библиотеки. Такое разделение выражает смысл файлов: каталог lib содержит код, который может использоваться другими целями, а каталог bin содержит точку входа программы. Директорию tests добавляют после появления отдельной цели тестов; в данном примере она намеренно не нужна.

project/ ├── CMakeLists.txt ├── bin/ │ ├── CMakeLists.txt │ └── main.cpp ├── lib/ │ ├── CMakeLists.txt │ ├── greeting.h │ └── greeting.cpp └── tests/ # добавляется после появления отдельной цели тестов
CMakeLists.txt — корень
cmake_minimum_required(VERSION 3.25)

project(cmake_practice LANGUAGES CXX)

add_subdirectory(lib)
add_subdirectory(bin)

add_subdirectory(lib) заставляет CMake перейти в каталог lib и прочитать его CMakeLists.txt. Там создаётся цель greeting. Затем add_subdirectory(bin) читает описание исполняемого файла. К этому моменту имя greeting уже известно CMake, поэтому bin/CMakeLists.txt может указать зависимость от него. Порядок здесь отражает смысловую связь: приложение использует библиотеку.

lib/CMakeLists.txt
add_library(greeting STATIC greeting.cpp)

target_include_directories(greeting
    PUBLIC
        "${CMAKE_CURRENT_SOURCE_DIR}"
)

target_compile_features(greeting PUBLIC cxx_std_20)
target_compile_options(greeting PRIVATE -Wall -Wextra -Wpedantic)

Команда add_library(greeting STATIC greeting.cpp) создаёт цель greeting и относит к ней файл greeting.cpp. При сборке этот файл будет скомпилирован, а его объектный файл войдёт в статическую библиотеку: обычно libgreeting.a на Linux/macOS и greeting.lib на Windows. Статическая библиотека не является самостоятельной программой: её код включается в исполняемый файл при линковке цели-потребителя.

CMAKE_CURRENT_SOURCE_DIR — путь к каталогу того CMakeLists.txt, который CMake обрабатывает в данный момент. Поэтому в данном файле выражение "${CMAKE_CURRENT_SOURCE_DIR}" означает каталог lib. Указание такого пути не зависит от того, из какой директории была запущена команда CMake.

bin/CMakeLists.txt
add_executable(app main.cpp)

target_link_libraries(app PRIVATE greeting)

Команда add_executable(app main.cpp) создаёт исполняемую цель app. Строка target_link_libraries(app PRIVATE greeting) одновременно задаёт порядок сборки и сообщает линковщику, что к app нужно присоединить библиотеку greeting. Не нужно вручную писать путь к файлу libgreeting.a или greeting.lib: CMake получает его из описания цели greeting.

7.1 Наследование include-пути

Заголовок greeting.h образует часть интерфейса библиотеки: чтобы вызвать print_greeting(), клиентский код должен его подключить. Поэтому путь к этому заголовку необходим не только при компиляции greeting.cpp, но и при компиляции main.cpp. Ключевое слово PUBLIC в target_include_directories выражает именно это требование: каталог применяется к библиотеке и передаётся всем целям, которые с ней связаны.

Цель app связывается с greeting. Следовательно, она автоматически получает публичный путь к заголовку. Отдельная строка target_include_directories(app ...) здесь была бы повторением одной и той же зависимости в двух местах. Если позже каталог заголовков библиотеки изменится, достаточно исправить настройку самой библиотеки.

7.2 PUBLIC, PRIVATE, INTERFACE

ОбластьПрименяется к целиПередаётся потребителямПример
PRIVATEДаНетВнутренний флаг или библиотека.
PUBLICДаДаКаталог заголовков библиотеки.
INTERFACEНетДаБиблиотека из заголовков.

Эти три слова применяются к свойствам цели: include-путям, требованиям стандарта, флагам и зависимостям. Их значение можно вывести из двух вопросов: нужно ли свойство самой цели и нужно ли оно потребителю этой цели. Если ответы «да, да» — PUBLIC; «да, нет» — PRIVATE; «нет, да» — INTERFACE.

Область зависимости

Исполняемый файл app обычно является конечной точкой графа: другие цели не используют его как библиотеку. Поэтому зависимость target_link_libraries(app PRIVATE greeting) не передаётся дальше. Для библиотеки область выбирают по её действительному интерфейсу, а не по названию команды.

Поэтому имя каталога отражает его содержимое и не допускает смешения отладочной и оптимизированной сборок. Наличие Ninja в текущем окружении можно проверить командой ninja --version.

7.4 Пример: Hello/Test

Рассмотрим проект из практики. В исходном варианте все файлы лежат рядом, а main.cpp подключает реализации через #include "test.cpp" и #include "lib.cpp". Такая запись смешивает текстовое включение заголовка с компиляцией исходных файлов. Корректная организация отделяет интерфейс от реализации и поручает CMake перечисление .cpp-файлов.

Функция Hello() печатает строку. Функция Test() вызывает Hello(), а затем печатает продолжение. Обе функции реализуют обычное поведение программы и вызываются из main(). Несмотря на имя файла, test.cpp в этом варианте не является набором unit-тестов; поэтому он входит в библиотеку вместе с lib.cpp.

practice-02/ ├── CMakeLists.txt ├── bin/ │ ├── CMakeLists.txt │ └── main.cpp └── lib/ ├── CMakeLists.txt ├── include/ │ ├── lib.hpp │ └── test.hpp └── src/ ├── lib.cpp └── test.cpp
CMakeLists.txt
cmake_minimum_required(VERSION 3.25)

project(practice_02 LANGUAGES CXX)

add_subdirectory(lib)
add_subdirectory(bin)

Корневой файл создаёт проект и последовательно подключает два подкаталога. Сначала обрабатывается lib, в котором появляется цель practice_lib. Затем обрабатывается bin, где исполняемый файл может сослаться на уже объявленную библиотеку.

lib/CMakeLists.txt
add_library(practice_lib STATIC
    src/lib.cpp
    src/test.cpp
)

target_include_directories(practice_lib
    PUBLIC
        "${CMAKE_CURRENT_SOURCE_DIR}/include"
)

target_compile_features(practice_lib PUBLIC cxx_std_20)
target_compile_options(practice_lib PRIVATE -Wall -Wextra -Wpedantic)

В lib/CMakeLists.txt перечислены два исходных файла с телами функций. Они компилируются как самостоятельные единицы трансляции и собираются в статическую библиотеку practice_lib. Каталог include объявлен публичным, потому что оба заголовка нужны не только самим файлам библиотеки, но и main.cpp. В примере требование cxx_std_20 также помечено как публичное: этим цель объявляет C++20 частью своего контракта с потребителями. Если публичные заголовки библиотеки не используют возможности C++20, более точный вариант — назначить требование PRIVATE библиотеке и задать стандарт отдельно каждой программе. Предупреждения назначены PRIVATE, так как это правило проверки внутренней реализации библиотеки, а не требование к её пользователю.

bin/CMakeLists.txt
add_executable(practice_02 main.cpp)

target_link_libraries(practice_02 PRIVATE practice_lib)

В каталоге bin находится единственная точка входа. Эта цель не перечисляет lib.cpp и test.cpp повторно: вместо этого она выражает зависимость от practice_lib. Через эту зависимость CMake передаёт include-путь и добавляет библиотеку в линковку.

lib/include/lib.hpp
#ifndef PRACTICE_LIB_HPP
#define PRACTICE_LIB_HPP

void Hello();

#endif  // PRACTICE_LIB_HPP
lib/include/test.hpp
#ifndef PRACTICE_TEST_HPP
#define PRACTICE_TEST_HPP

void Test();

#endif  // PRACTICE_TEST_HPP
lib/src/lib.cpp
#include "lib.hpp"

#include <iostream>

void Hello() {
    std::cout << "Hello world! ";
}
lib/src/test.cpp
#include "test.hpp"

#include "lib.hpp"
#include <iostream>

void Test() {
    Hello();
    std::cout << "+ Test\n";
}
bin/main.cpp
#include "lib.hpp"
#include "test.hpp"

#include <iostream>

int main() {
    Hello();
    std::cout << '\n';
    Test();
}
Логическая связь файлов

Файл main.cpp включает только lib.hpp и test.hpp, то есть объявления Hello() и Test(). Файл test.cpp включает lib.hpp, потому что его реализация вызывает Hello(). Реализации перечислены ровно один раз в add_library. После этого target_link_libraries соединяет вызовы из main.cpp с определениями в practice_lib.

./build/bin/practice_02

8. Генераторы и конфигурации

Генератор — часть CMake, которая переводит описание целей в формат конкретной системы сборки. Один и тот же CMakeLists.txt можно настроить для Ninja, Make, Visual Studio или Xcode. Генератор не меняет правила C++ и не является компилятором; он определяет, какие служебные файлы появятся в дереве сборки и какая программа будет управлять следующей стадией.

bash / PowerShell
cmake --help

Существенное различие генераторов — способ хранения конфигураций. Конфигурация сборки — набор настроек, прежде всего оптимизаций и отладочной информации. Обычно используют Debug для отладки и Release для оптимизированной программы. Ninja и Unix Makefiles — одноконфигурационные генераторы: один каталог сборки хранит одну конфигурацию. Visual Studio, Xcode и Ninja Multi-Config — многоконфигурационные: один каталог умеет хранить несколько конфигураций.

Тип генератораКогда выбирается Debug/ReleaseКорректная команда
Одноконфигурационный: Ninja, Unix MakefilesПри configure. Одна папка build — одна конфигурация.cmake -S . -B build-debug -DCMAKE_BUILD_TYPE=Debug
Многоконфигурационный: Visual Studio, Xcode, Ninja Multi-ConfigПри build. Одна папка build хранит несколько конфигураций.cmake --build build --config Debug
Значение CMAKE_BUILD_TYPE

Переменная CMAKE_BUILD_TYPE применяется только к одноконфигурационным генераторам. Для Visual Studio и Xcode она не выбирает конфигурацию, потому что в одном проекте уже существуют несколько вариантов. В таком случае конфигурацию указывают при сборке: cmake --build build --config Debug либо cmake --build build --config Release. Таким образом, место выбора конфигурации определяется типом генератора.

Windows и Clang

Visual Studio — IDE-генератор. Для него компилятор не задают через CMAKE_CXX_COMPILER; набор инструментов выбирают параметром -T. Во всех примерах этого конспекта требуется именно командный компилятор clang++, поэтому на Windows выбран Ninja. Такой выбор делает команды configure и build одинаковыми по смыслу на трёх операционных системах.

ОСЧто меняетсяЧто остаётся одинаковым

Генератор и путь к компилятору не помещают в CMakeLists.txt. Эти значения описывают конкретную машину и конкретное дерево сборки, а не сам проект. Их задают параметрами configure, чтобы один исходный текст оставался переносимым между Linux, macOS и Windows.

9. Стандарт C++, предупреждения и макросы

9.1 Стандарт языка и предупреждения

Параметры компиляции принадлежат конкретной цели. Поэтому их задают командами семейства target_*, а не общей переменной CMAKE_CXX_FLAGS. У разных библиотек и программ в одном проекте могут быть разные требования к стандарту языка и разные правила предупреждений. Привязка параметра к цели сохраняет эту информацию в графе зависимостей.

CMake
target_compile_features(greeting PUBLIC cxx_std_20)

target_compile_options(app PRIVATE
    -Wall
    -Wextra
    -Wpedantic
)
  • cxx_std_20 означает, что цель требует возможностей C++20. Если это публичное свойство библиотеки, оно передаётся потребителям: их исходники будут компилироваться по совместимому стандарту.
  • -Wall, -Wextra и -Wpedantic — параметры диагностики Clang. Они не изменяют смысл правильной программы, но просят компилятор сообщать о большем числе подозрительных конструкций.
  • -Werror меняет статус предупреждений: любое выбранное предупреждение становится ошибкой и останавливает сборку. Этот режим имеет смысл включать только тогда, когда команда готова поддерживать его постоянно.
Зависимость от компилятора

-Wall, -Wextra и -Wpedantic — флаги Clang и GCC. В MSVC им соответствуют другие параметры. Поскольку команды этого конспекта используют clang++ и Ninja, приведённые флаги одинаково применимы на Linux, macOS и Windows при установленном Clang.

9.2 Две разные опции -D

Где написаноПримерЧто делает
Командная строка CMakecmake -S . -B build -DMY_OPTION=ONПередаёт CMake значение переменной cache при configure.
Командная строка Clangclang++ -DAPP_VERSION=1 main.cppОпределяет макрос препроцессора для конкретной компиляции.
CMake target-командаtarget_compile_definitions(app PRIVATE APP_VERSION=1)Передаёт -DAPP_VERSION=1 только указанной цели.

Одинаковая буква -D обозначает разные действия в зависимости от программы. У CMake она передаёт значение переменной на этапе configure. У Clang она создаёт макрос препроцессора для одного вызова компилятора. Поэтому переменная CMake не становится макросом в C++ автоматически. Чтобы передать макрос именно цели CMake, используют target_compile_definitions:

C++
#if APP_VERSION == 1
    // код для первой версии
#endif

Функциональные макросы в командной строке содержат скобки и запятые, которые оболочка может интерпретировать отдельно. Поэтому они требуют экранирования и плохо подходят для настройки сборки. Логику с параметрами выражают обычной функцией C++; макрос через target_compile_definitions оставляют для значения, которое должно быть известно препроцессору до компиляции.

9.3 Список исходников

Состав каждой цели перечисляют явно:

CMake

    greeting.cpp
)

Команда file(GLOB) находит файлы по маске, но добавление нового .cpp не всегда заставляет CMake повторно выполнить configure. В результате новый файл может остаться вне сборки без явной ошибки. Явный список показывает состав цели при чтении CMakeLists.txt и делает изменение исходников заметным в системе контроля версий.

10. Работа с файлами: <fstream>

Заголовок <fstream> определяет файловые потоки — объекты, через которые программа читает данные из файла и записывает данные в файл. Поток хранит не только сам файл, но и состояние операции: удалось ли открыть файл, дошло ли чтение до конца и произошла ли ошибка формата. Поэтому открытие и ввод необходимо проверять отдельно.

КлассНазначениеРежим по умолчанию
std::ifstreamЧтение из файла.std::ios::in
std::ofstreamЗапись в файл.std::ios::out | std::ios::trunc
std::fstreamЧтение и запись.Режим указывают явно.
C++
#include <fstream>
#include <iostream>
#include <string>

int main() {
    std::ifstream input{"input.txt"};
    if (!input) {
        std::cerr << "Cannot open input.txt\n";
        return 1;
    }

    int value = 0;
    if (!(input >> value)) {
        std::cerr << "Expected an integer\n";
        return 1;
    }

    std::ofstream output{"out.txt"};
    if (!output) {
        std::cerr << "Cannot create out.txt\n";
        return 1;
    }

    output << "Value: " << value << '\n';
}

10.1 Разбор

  1. std::ifstream input{"input.txt"} создаёт поток чтения и сразу пытается открыть файл. Конструктор не обязан выбрасывать исключение при неудаче: состояние ошибки остаётся внутри объекта.
  2. Выражение if (!input) проверяет это состояние. Если файла нет, нет прав на чтение или путь неверен, программа выводит сообщение в std::cerr и завершает работу с кодом 1. Без этой проверки следующая операция чтения молча не даст значения.
  3. Выражение input >> value пытается прочитать один целый токен, предварительно пропуская пробельные символы. Результат операции можно проверить в условии: if (!(input >> value)) срабатывает, если файл закончился раньше времени или следующий фрагмент не является целым числом.
  4. std::ofstream output{"out.txt"} открывает файл для записи. По умолчанию он создаёт новый файл либо очищает существующий, потому что использует режим std::ios::trunc. Для дописывания в конец указывают режим std::ios::app.
  5. Оператор << преобразует значение в текст и записывает его в поток. При выходе из области видимости деструктор потока закрывает файл и завершает запись. Это применение RAII: ресурс принадлежит объекту и освобождается автоматически.
Относительный путь

Строка "input.txt" не означает «файл рядом с main.cpp». Это относительный путь от рабочей директории запущенного процесса. При запуске из терминала ею обычно является каталог, из которого была введена команда. В IDE рабочая директория задаётся в настройках запуска. Поэтому одно и то же приложение может находить файл в терминале и не находить его при запуске из IDE.

Оператор >> читает отдельный токен и не сохраняет пробелы внутри текста. Если нужна целая строка, используют std::getline(input, line). После чтения числа через >> перед getline обычно остаётся символ конца строки; выражение std::getline(input >> std::ws, line) сначала пропускает этот пробельный остаток, а затем читает строку.

Проверка

Перед запуском проекта каждый файл должен быть соотнесён с этапом, на котором он участвует. Следующие утверждения выражают основные инварианты многофайловой программы и CMake-проекта.

  • Каждый .cpp включён в одну цель CMake либо один раз передан команде clang++; через #include подключаются только заголовки.
  • Публичное объявление помещено в заголовок, который защищён include guard или #pragma once; тело обычной функции находится в одном .cpp-файле.
  • Пути поиска заголовков задаются target_include_directories, а зависимость от библиотеки — target_link_libraries. Эти две команды решают разные задачи.
  • Зависимость исполняемого файла обычно имеет область PRIVATE, поскольку исполняемый файл не образует интерфейс для других целей.
  • Результаты configure и build находятся вне исходного дерева, например в build-debug.
  • Компилятор и генератор выбираются при первом configure нового дерева сборки. Для их смены используется новый каталог сборки.
  • Для одноконфигурационного генератора выбран CMAKE_BUILD_TYPE; для многоконфигурационного вариант указывается через --config.
  • Файловые потоки проверяются после открытия и после ввода, а относительные пути рассматриваются относительно рабочей директории программы.
