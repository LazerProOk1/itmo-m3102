## Архитектура фон Неймана и иерархия памяти

### Архитектура фон Неймана

В архитектуре фон Неймана у компьютера есть процессор, **общая память для команд и данных**, а также устройства ввода и вывода. Программа (машинный код) и обрабатываемые ею данные хранятся в одной и той же памяти и доступны процессору одинаковым образом — по адресам.

```diagram

caption: Команды и данные лежат в одной общей памяти
CPU: box "Процессор"
MEM: db "Память: команды и данные"
IN: round "Ввод"
OUT: round "Вывод"
IN -> CPU
CPU -> MEM : чтение и запись
MEM -> CPU
CPU -> OUT
```

### Иерархия памяти

Чем ближе память к ядру процессора, тем обычно **меньше её объём и меньше задержка доступа**. И наоборот: чем дальше от ядра, тем память больше, но медленнее.

| Уровень | Примерный порядок объёма | Где находится |
|---|---|---|
| Регистры | Сотни B — единицы KiB | Набор регистров одного ядра |
| Кеш L1 | Десятки — сотни KiB | Обычно на ядро; команды и данные отдельно |
| Кеш L2 | Сотни KiB — единицы MiB | На ядро или группу ядер |
| Кеш L3, если есть | Единицы — сотни MiB | Общий для группы ядер или процессора |
| RAM | Единицы — сотни GiB | Оперативная память компьютера |
| SSD | Сотни GiB — единицы TiB | Постоянное хранилище |

```diagram

caption: Слева направо объём растёт, но растёт и задержка доступа
R: box "Регистры"
L1: box "Кеш L1"
L2: box "Кеш L2"
L3: box "Кеш L3 (если есть)"
RAM: box "RAM"
SSD: db "SSD"
R -> L1
L1 -> L2
L2 -> L3
L3 -> RAM
RAM -> SSD
```

:::note
Объёмы в таблице — **порядки величин**, а не точные значения: они зависят от конкретного процессора и компьютера.
:::

## Процессы, потоки и виртуальное адресное пространство

### Процессы и потоки

**Процесс** — выполняющаяся программа со своими ресурсами:

- независимое адресное пространство;
- объекты ядра: файловые дескрипторы, объекты синхронизации и т. д.

**Потоки одного процесса** выполняются внутри него и делят между собой часть ресурсов, но имеют и собственные:

- *общее* для всех потоков: адресное пространство — код, глобальные данные, динамическая память;
- *собственное* у каждого потока: стек и контекст выполнения — регистры и позиция выполнения (то, какая инструкция выполняется следующей).

Когда ОС переключает потоки на ядре, она **сохраняет** контекст уходящего потока и **восстанавливает** контекст того, который начинает выполняться. Так два потока одного процесса могут поочерёдно выполняться на одном ядре, и каждый продолжает с того места, где остановился.

:::warning
Собственный стек потока **не изолирован** от других потоков. Стек «принадлежит» потоку лишь в том смысле, что именно по нему поток хранит свои вызовы. Но адресное пространство общее, поэтому другой поток, имея указатель, может обращаться к этой памяти.
:::

### Виртуальная память и таблицы страниц

Каждый процесс работает со **своими виртуальными адресами**. У процесса создаётся «иллюзия» обладания всей памятью: он обращается по адресам так, будто память принадлежит только ему.

Как это устроено:

- ОС задаёт отображения страниц и права доступа в **таблицах страниц** (*page tables*);
- процессор использует эти таблицы, чтобы переводить виртуальные адреса в физические;
- один и тот же адрес в двух разных процессах может указывать на **разные страницы RAM**;
- общая память и файлы могут отображаться сразу в несколько процессов.

```graph directed

layout: layered

```

:::meaning
**Таблица страниц** (*page table*) — структура, в которой ОС хранит для страниц процесса их отображение на физическую память и права доступа. Процессор применяет её при каждом переводе виртуального адреса в физический.
:::

:::warning
Размер адресного пространства $\neq$ объём RAM. Часть адресов не отображена или защищена, а выделение памяти может завершиться неудачей.
:::

### Если страницы нет в памяти

:::meaning
**Page fault** — исключение, возникающее при обращении к странице, которая сейчас недоступна или не допускает запрошенную операцию. После этого ОС выясняет причину.
:::

Возможные причины и реакция ОС:

- **Swap** — страницу выгрузили на диск; ОС возвращает её в RAM.
- **Отображение файла** — содержимое ещё не загружено; ОС читает нужную часть файла.
- **Ленивое выделение** — адреса зарезервированы, а физическая память предоставляется при первом обращении.
- **Недопустимый доступ** — нужного отображения или разрешения нет; на Linux процесс обычно получает сигнал `SIGSEGV`.

Если ОС смогла обеспечить доступ, выполнение продолжается так, как будто ничего не произошло.

```diagram
title: Что происходит при обращении к странице
A: round "Обращение к адресу"
B: diamond "Страница доступна?"
C: box "Доступ выполнен"
D: box "Page fault"
E: diamond "ОС смогла обеспечить доступ?"
F: box "Swap, чтение файла или ленивое выделение"
G: box "SIGSEGV (Linux)"
A -> B
B -> C : Да
B -> D : Нет
D -> E
E -> F : Да
F -> C : Выполнение продолжается
E -> G : Нет, недопустимый доступ
```

:::warning
Сам по себе page fault **не означает ошибку программы**. Ошибкой он становится лишь в случае недопустимого доступа.
:::

## Сегменты программы и представление данных в памяти

### Адресное пространство: ОС и платформа

Адресное пространство процесса устроено по-разному на разных ОС и архитектурах. В 32-битных схемах оно делится между программой и ядром ОС: на Linux x86 в пропорции $3/1$, на Windows x86 — $2/2$. Для x86-64 и macOS ARM64 раскладка другая, и на лекции она показана схематично.

### Адресное пространство процесса Linux: 32-битная схема

Области адресного пространства сверху вниз (от старших адресов к младшим):

```graph
title: Адресное пространство процесса Linux x86 (схема)
caption: Промежутки между областями не отображены (unmapped)
layout: manual
H "Старшие адреса" @ 80, 15
K "Kernel: область ядра ОС" @ 320, 20 {color: red}
S "Stack: стек потока" @ 320, 60
M "Отображения файлов и библиотек" @ 320, 100
HP "Heap: куча" @ 320, 140
B "bss: нулевые начальные значения" @ 320, 180
D "data: заданные начальные значения" @ 320, 220
R "rodata: только чтение, строковые литералы" @ 320, 260
T "text: машинный код" @ 320, 300 {color: blue}
L "Младшие адреса" @ 80, 340
K -- S
S -- M
M -- HP
HP -- B
B -- D
D -- R
R -- T
```

- **Kernel** — область ядра ОС.
- **Stack** — стек потока.
- **File and library mappings** — отображения файлов, библиотек и анонимные отображения.
- **Heap** — классическая область кучи.
- **bss** — данные с начальным нулевым значением.
- **data** — данные с заданными начальными значениями.
- **rodata** — данные только для чтения, в том числе строковые литералы.
- **text** — машинный код.
- **Unmapped** — промежутки без отображения.

От чего зависит реальная раскладка:

- ОС и формат исполняемого файла: ELF в Linux, Mach-O в macOS, PE в Windows;
- архитектура и ABI: разрядность адресов, выравнивание и соглашения платформы;
- сборка и запуск: компоновщик, загрузчик, библиотеки, аллокатор и ASLR.

:::note
Стеков и областей динамической памяти может быть несколько. Аллокатор может использовать и heap, и отдельные отображения.
:::

:::warning
Секции файла (`text`, `rodata`, `data`, `bss`) и области адресного пространства — **разные уровни описания**: одно описывает содержимое файла программы, другое — то, как оно отображено в память запущенного процесса.
:::

### Что где лежит: типичная схема Linux / ELF

| Объект | Пример | Область | Типичные права |
|---|---|---|---|
| Машинный код | Тело функции | text | `r-x` |
| Строковые литералы | `"Hello world"` | rodata | `r--` |
| Глобальные данные с ненулевым значением | `int counter = 42;` | data | `rw-` |
| Глобальные данные с начальным нулём | `int total;` | bss | `rw-` |
| Динамический объект | `new int{42}` | heap / анонимное отображение | `rw-` |
| Локальный объект, если он в памяти | `int local;` | stack | `rw-` |
| Библиотеки и отображённые файлы | Результат `mmap` | Отдельные отображения | Зависит от области |

:::meaning
Права доступа: `r` — чтение, `w` — запись, `x` — исполнение. Права задаются **страницам памяти**; несколько секций файла могут попадать в один сегмент.
:::

:::note
Формулировка «локальный объект, если он в памяти» неслучайна: компилятор может держать локальную переменную не в памяти стека, а в регистре.
:::

### Адреса объектов и функции

Программа печатает адреса объектов разных видов, чтобы потом сопоставить их с областями памяти процесса.

```cpp
// memory-addresses.cpp
#include <cstdio>
#include <print>
#include <unistd.h> // POSIX (Linux/macOS): getpid, not standard C++.

const double pi = 3.141592653589793;
int initialized_global = 42;
int zero_initialized_global;

void some_function() {}

int main() {
    int local = 0;
    const char* text = "Hello world";
    int* dynamic = new int{42};

    std::println("Process ID: {}", static_cast<long>(getpid()));
    std::println("Constant: {}", static_cast<const void*>(&pi));
    std::println("Initialized global: {}", static_cast<void*>(&initialized_global));
    std::println("Zero-initialized global: {}", static_cast<void*>(&zero_initialized_global));
    std::println("String literal: {}", static_cast<const void*>(text));
    // POSIX supports converting a function pointer to void*.
    std::println("Function: {}", reinterpret_cast<void*>(&some_function));
    std::println("Local variable: {}", static_cast<void*>(&local));
    std::println("Dynamic object: {}", static_cast<void*>(dynamic));
    std::println("Press Enter to exit.");
    std::getchar();
    delete dynamic;
}
```

Разбор программы:

1. Объявлены константа `pi`, глобальная переменная с начальным значением `42`, глобальная переменная без начального значения и пустая функция.
2. В `main` создаются локальная переменная `local`, указатель на строковый литерал и динамический объект `new int{42}`.
3. Для каждого объекта печатается адрес. Приведение к `void*` нужно, чтобы вывести именно адрес, а не значение.
4. Адрес функции приводится к `void*` через `reinterpret_cast`; POSIX допускает такое преобразование.
5. `getpid` (POSIX, не стандартный C++) возвращает идентификатор процесса. Программа ждёт нажатия Enter, чтобы процесс оставался жив, пока мы смотрим его карту памяти.

### Карта памяти запущенного процесса

Запустите пример выше. Пока программа ждёт Enter, возьмите её PID и выполните в другом терминале команду для просмотра карты памяти:

| ОС | Команда для карты памяти |
|---|---|
| Linux | `cat /proc/31707/maps` |
| macOS | `vmmap -interleaved 31707` |
| Windows | `vmmap.exe -p 31707` |

На Windows используется утилита Sysinternals VMMap, которая открывает карту в окне.

Фрагмент карты того же запуска на Mac:

```text
Область       Начало       Конец        Права
__TEXT        10089c000    1008c0000    r-x
__DATA        1008c4000    1008c8000    rw-
MALLOC_TINY   100f58000    101358000    rw-
Stack         16ed68000    16f564000    rw-
```

Вывод программы на этом Mac (ARM64):

```text
Process ID: 31707
Constant: 0x1008b8a18
Initialized global: 0x1008c4000
Zero-initialized global: 0x1008c4004
String literal: 0x1008bbc96
Function: 0x10089c670
Local variable: 0x16f561bf8
Dynamic object: 0x100f69bb0
Press Enter to exit.
```

:::example
Сопоставим адреса с диапазонами карты. Конец диапазона не включён.

1. Функция `some_function`: `0x10089c670` лежит между `10089c000` и `1008c0000`, то есть в `__TEXT` (код, права `r-x`).
2. Глобальные переменные: `0x1008c4000` и `0x1008c4004` лежат между `1008c4000` и `1008c8000`, то есть в `__DATA` (права `rw-`). Обратите внимание: две глобальные переменные идут рядом, на расстоянии `4`.
3. Динамический объект: `0x100f69bb0` попадает в диапазон `100f58000`–`101358000`, то есть в `MALLOC_TINY`.
4. Локальная переменная: `0x16f561bf8` попадает в диапазон `16ed68000`–`16f564000`, то есть в `Stack`.
:::

:::note
Адреса константы `pi` и строкового литерала также попадают в диапазон `__TEXT` — то есть в область только для чтения, а не в область записываемых данных.
:::

:::warning
При новом запуске PID и адреса изменятся, поэтому конкретные числа здесь иллюстрируют лишь *соответствие видов объектов областям*.
:::

```quiz
explain: Динамический объект, созданный через new, размещается в области, которой управляет аллокатор.
```

## Стек вызовов и время жизни локальных объектов

### Стек вызовов: передача аргументов и результат

Разберём, как вызов функции выглядит на уровне машинных команд для x86-64 и соглашения System V ABI. Исходный код:

```cpp
// function-call.cpp
int add(int a, int b) {
    int result = a + b;
    return result;
}

int main() {
    int a = 40;
    int b = 2;
    int answer = add(a, b);
    return answer;
}
```

Соглашение System V: первые два целочисленных аргумента передаются в `EDI` и `ESI`, результат типа `int` возвращается в `EAX`.

Получившийся ассемблерный код (Godbolt):

```asm
"add(int, int)":
        push    rbp
        mov     rbp, rsp
        mov     DWORD PTR [rbp-20], edi
        mov     DWORD PTR [rbp-24], esi
        mov     edx, DWORD PTR [rbp-20]
        mov     eax, DWORD PTR [rbp-24]
        add     eax, edx
        mov     DWORD PTR [rbp-4], eax
        mov     eax, DWORD PTR [rbp-4]
        pop     rbp
        ret
"main":
        push    rbp
        mov     rbp, rsp
        sub     rsp, 16
        mov     DWORD PTR [rbp-4], 40
        mov     DWORD PTR [rbp-8], 2
        mov     edx, DWORD PTR [rbp-8]
        mov     eax, DWORD PTR [rbp-4]
        mov     esi, edx
        mov     edi, eax
        call    "add(int, int)"
        mov     DWORD PTR [rbp-12], eax
        mov     eax, DWORD PTR [rbp-12]
        leave
        ret
```

:::meaning
**Red zone** — до $128$ байт памяти ниже `RSP`, которые функция может использовать для локальных данных без смещения `RSP`. В этом листинге `add` использует red zone: она не выделяет локальную область командой `sub rsp`, а обращается к ячейкам `[rbp-4]`, `[rbp-20]` и `[rbp-24]` прямо под текущей вершиной стека. Функция `main` же выделяет себе локальную область командой `sub rsp, 16`.
:::

### Регистры x86-64: названия и роли

**Регистр** — небольшое хранилище внутри процессора. Обозначение, начинающееся с `R`, — это 64-битный регистр, а начинающееся с `E` — его младшие 32 бита. Например, `EAX` — часть `RAX`.

| Регистр | Название | Роль в нашем листинге |
|---|---|---|
| `RDI` / `EDI` | Destination Index | Первый аргумент `a = 40` |
| `RSI` / `ESI` | Source Index | Второй аргумент `b = 2` |
| `RDX` / `EDX` | Data | Временное значение: `b` в `main`, `a` в `add` |
| `RAX` / `EAX` | Accumulator | Операнд сложения и результат `42` |
| `RSP` | Stack Pointer | Адрес текущей вершины стека |
| `RBP` | Base Pointer | Опорный адрес кадра функции |
| `RIP` | Instruction Pointer | Адрес следующей исполняемой инструкции |

:::warning
Названия регистров **исторические**: реальное назначение зависит от инструкции и от ABI — соглашений платформы. В нашем примере действует System V: первые два целочисленных аргумента — в `EDI`/`ESI`, результат `int` — в `EAX`. На другой платформе роли могут быть другими.
:::

### Вызов функции по шагам

:::example
Проследим выполнение программы по ассемблерному листингу. Смещения вида `[rbp-4]` отсчитываются от значения `RBP` *в той функции, где команда выполняется*.

**Начало `main`.**

1. `push rbp` — сохраняем прежнее значение `RBP`; `mov rbp, rsp` — теперь `RBP` указывает на опорную точку кадра `main`.
2. `sub rsp, 16` — отводим под локальные переменные `16` байт.
3. `mov DWORD PTR [rbp-4], 40` записывает `a = 40`, а `mov DWORD PTR [rbp-8], 2` записывает `b = 2`. Для `answer` отведена ячейка `[rbp-12]`.

**Подготовка вызова `add(a, b)`.**

4. `mov edx, [rbp-8]` и `mov eax, [rbp-4]` читают `b` и `a` во временные регистры.
5. `mov esi, edx` кладёт `b` во второй аргумент, `mov edi, eax` кладёт `a` в первый аргумент.
6. `call "add(int, int)"` передаёт управление функции `add`.

**Внутри `add`.**

7. `push rbp` и `mov rbp, rsp` создают кадр `add`.
8. Аргументы из `EDI` и `ESI` сохраняются в ячейки `[rbp-20]` и `[rbp-24]` — это red zone, `RSP` не двигается.
9. `mov edx, [rbp-20]` читает `a` (в `EDX` теперь `40`), `mov eax, [rbp-24]` читает `b` (в `EAX` теперь `2`).
10. `add eax, edx` складывает: в `EAX` получается $40 + 2 = 42$.
11. Значение записывается в `result` — ячейку `[rbp-4]` — и тут же читается обратно в `EAX`: это возвращаемое значение.
12. `pop rbp` восстанавливает `RBP` вызывающей функции, `ret` возвращает управление в `main`.

**Возврат в `main`.**

13. `mov [rbp-12], eax` записывает результат $42$ в `answer`, затем он снова читается в `EAX`.
14. `leave` убирает кадр `main`, `ret` завершает программу; `EAX` $= 42$ — результат `main`.
:::


Расположение локальных данных в кадрах этого примера:

| Функция | Ячейка | Что хранится |
|---|---|---|
| `main` | `[rbp-4]` | `a = 40` |
| `main` | `[rbp-8]` | `b = 2` |
| `main` | `[rbp-12]` | `answer` (получает `42`) |
| `add` | `[rbp-4]` | `result` |
| `add` | `[rbp-20]` | копия аргумента `a` (red zone) |
| `add` | `[rbp-24]` | копия аргумента `b` (red zone) |

### Длительность хранения — storage duration

**Storage duration** описывает, как долго существует память для объекта.

| Вид | Пример объявления | Как долго существует память |
|---|---|---|
| Automatic | Обычная локальная переменная | До выхода из её блока |
| Static | Глобальная переменная или локальная `static` | На протяжении работы программы |
| Thread | Переменная `thread_local` | На протяжении работы соответствующего потока |
| Dynamic | Объект, созданный обычным `new` | До освобождения выделенной памяти |

:::note
Это категории языка C++. Стек и куча — лишь **типичные способы реализации** хранения: automatic-объекты обычно живут в стеке, dynamic — в куче.
:::

### Область видимости и хранение

`static` у локальной переменной означает, что она инициализируется **один раз** и сохраняет значение между вызовами функции. Её имя при этом по-прежнему доступно только внутри блока, где она объявлена: время жизни и область видимости — разные вещи.

```cpp
// automatic-and-static.cpp
#include <print>

void visit() {
    int automatic_count = 0;
    static int static_count = 0;
    ++automatic_count;
    ++static_count;
    std::println("{} {}", automatic_count, static_count);
}

int main() {
    visit();
    visit();
}
```

:::example
Проследим два вызова `visit()`.

1. **Первый вызов.** Создаются `automatic_count = 0` и (однократно) `static_count = 0`. После инкремента обе равны `1`. Печатается `1 1`. При выходе из функции `automatic_count` исчезает, а `static_count` остаётся.
2. **Второй вызов.** `automatic_count` создаётся заново и снова равна `0`. Инициализация `static_count` не повторяется: она уже равна `1`. После инкремента: `automatic_count = 1`, `static_count = 2`. Печатается `1 2`.
:::

## Куча, malloc/free и new/delete

### Heap (куча)

Динамические объекты обладают такими свойствами:

- динамический объект может **пережить выход из функции**, которая его создала;
- его размер можно выбрать **во время выполнения**;
- освобождение памяти должно быть предусмотрено программой (позже будут изучены средства, берущие освобождение на себя).

:::warning
Размер объекта — не главное отличие: даже один `int` может требовать динамического времени жизни, если он должен пережить функцию.
:::

:::note
Не путайте: **куча** (*heap*) как область динамической памяти и **куча** как структура данных, например двоичная куча для очереди с приоритетом, — разные понятия. Совпадение названий не означает, что динамическая память организована в виде такой структуры.
:::

### Объект переживает создавшую его функцию

```cpp
// dynamic-lifetime.cpp
#include <print>

int* make_value() {
    int* value = new int{42};
    return value;
}

int main() {
    int* value = make_value();
    std::println("{}", *value);
    delete value;
}
```

:::example
Разберём по шагам.

1. В `make_value` создаётся динамический объект `new int{42}`, а локальная переменная-указатель `value` хранит его адрес.
2. `return value` возвращает **копию адреса** вызывающей функции.
3. При выходе из `make_value` локальный указатель `value` (automatic-объект) исчезает, но объект, созданный через `new`, **остаётся**.
4. В `main` свой указатель `value` получает копию адреса, и `*value` печатает `42`.
5. Освобождение выполняет вызывающий код: `delete value`.
:::

### Функции работы с памятью из `<cstdlib>`

| Функция | Что делает |
|---|---|
| `malloc(size)` | Выделяет `size` байт без инициализации содержимого |
| `calloc(count, size)` | Выделяет $\text{count} \times \text{size}$ байт и обнуляет их |
| `realloc(pointer, size)` | Меняет размер блока; может переместить его |
| `free(pointer)` | Освобождает блок; `free(nullptr)` ничего не делает |

Для ненулевого запрошенного размера ошибка выделения означает возврат `nullptr`.

:::warning
Если `realloc` завершился неудачей, старый блок **остаётся выделенным**: его указатель нельзя терять.
:::

### malloc: выделение и освобождение

```cpp
// malloc-array.cpp
#include <print>
#include <cstdlib>

int main() {
    int* values = static_cast<int*>(std::malloc(4 * sizeof(int)));
    if (values == nullptr) {
        return 1;
    }

    for (int index = 0; index < 4; ++index) {
        values[index] = index * index;
        std::println("values[{}] = {}", index, values[index]);
    }
    std::free(values);
}
```

:::example
Разбор программы.

1. `malloc(4 * sizeof(int))` запрашивает память на четыре `int`. Содержимое блока не инициализировано.
2. Результат — `void*`. В C++ его нужно явно преобразовать в `int*`, это делает `static_cast`.
3. Если выделение не удалось, `malloc` вернул `nullptr`, и программа завершается с кодом `1`.
4. Цикл **записывает** в каждый элемент значение $\text{index}^2$, а затем печатает его. Читать элементы до записи нельзя — они не заданы.
5. Печатается: `values[0] = 0`, `values[1] = 1`, `values[2] = 4`, `values[3] = 9`.
6. `std::free(values)` освобождает блок.
:::

```array
title: Массив values после цикла
[0, 1, 4, 9] i=3
```

### Проверка выделения и освобождение памяти

- Если выделение не удалось, `malloc` возвращает `nullptr`.
- Память освобождаем через `std::free` **ровно один раз**.
- `std::free(nullptr)` ничего не делает.
- После освобождения указатель нельзя разыменовывать.
- Присваивание `nullptr` одной переменной не исправляет другие копии указателя.

### free не обнуляет указатель

```cpp
// free-and-nullptr.cpp
#include <cstdlib>
#include <print>

int main() {
    int* pointer = static_cast<int*>(std::malloc(sizeof(int)));
    if (pointer == nullptr) {
        return 1;
    }
    *pointer = 42;
    std::println("Before free: {}", *pointer);

    std::free(pointer); // Releases the block; pointer is now dangling.
    pointer = nullptr;  // Explicit assignment, not an effect of free.

    std::println("pointer == nullptr: {}", pointer == nullptr);
    std::free(pointer); // free(nullptr) does nothing.
}
```

`free` освобождает выделенный блок, но **не присваивает** переменной `pointer` значение `nullptr` и не гарантирует обнуления байтов блока. После `free` указатель становится **висячим** (*dangling*): он хранит адрес блока, которого больше нет. Следующей строкой программа явно присваивает ему `nullptr`.

:::example
Проследим:

1. Выделяем блок под один `int`, записываем `42` и печатаем `Before free: 42`.
2. `std::free(pointer)` освобождает блок. Переменная `pointer` по-прежнему хранит старый адрес — она висячая.
3. `pointer = nullptr` — **явное** присваивание, а не эффект `free`.
4. Печатается `pointer == nullptr: true`.
5. Повторный `std::free(pointer)` безопасен именно потому, что `pointer` теперь `nullptr`, а `free(nullptr)` ничего не делает.
:::

### calloc

```cpp
// calloc-array.cpp
#include <print>
#include <cstdlib>

int main() {
    int* values = static_cast<int*>(std::calloc(4, sizeof(int)));
    if (values == nullptr) {
        return 1;
    }

    for (int index = 0; index < 4; ++index) {
        std::println("values[{}] = {}", index, values[index]);
    }
    std::free(values);
}
```

`calloc` получает **количество элементов** и **размер одного элемента**, затем обнуляет выделенные байты. Для массива `int` это даёт нулевые значения, поэтому печатаются четыре строки `values[i] = 0`. В отличие от `malloc`, читать элементы можно сразу.

### Указатель и объект: разные адреса и размеры

```cpp
// pointer-and-object.cpp
#include <print>
#include <cstdlib>

int main() {
    int local = 0;
    int* pointer = static_cast<int*>(std::malloc(sizeof(int)));
    if (pointer == nullptr) {
        return 1;
    }
    *pointer = 42;

    std::println("local: size={}, address={}", sizeof(local), static_cast<void*>(&local));
    std::println("pointer: size={}, address={}", sizeof(pointer), static_cast<void*>(&pointer));
    std::println("*pointer: size={}, address={}", sizeof(*pointer), static_cast<void*>(pointer));
    std::println("value={}", *pointer);
    std::free(pointer);
}
```

:::meaning
- `&pointer` — адрес **переменной-указателя** (она сама лежит в памяти, в данном случае в стеке).
- `pointer` — значение указателя, то есть адрес **выделенного объекта**.
- `sizeof(pointer)` измеряет размер самого указателя, а `sizeof(*pointer)` — размер объекта типа `int`, на который он указывает.
:::

Поэтому в программе у `pointer` и `*pointer` разные размеры, а для `pointer` и `*pointer` печатаются разные адреса: адрес переменной-указателя и адрес динамического объекта.

### new и delete

```cpp
// new-delete.cpp
int main() {
    int* value = new int;
    delete value;

    int* array = new int[10];
    delete[] array;

    return 0;
}
```

- `new int` — без начального значения; до чтения нужна запись.
- `new int{}` — значение `0`.
- `new int{42}` — значение `42`.
- `delete` освобождает одиночный объект, `delete[]` — массив.
- При неудаче выделения обычный `new` бросает `std::bad_alloc` (исключения будут разобраны позже).

:::note
Для классов `new` может вызвать конструктор, а `delete` вызывает деструктор. К этому вернёмся при изучении классов.
:::

### new/delete и malloc/free: какой способ выбрать

| Выделение | Освобождение |
|---|---|
| `malloc`, `calloc`, `realloc` | `free` |
| `new T` | `delete` |
| `new T[n]` | `delete[]` |

:::warning
Способ освобождения определяется способом выделения. **Смешивание пар приводит к неопределённому поведению.**
:::

- `malloc` подходит, если нужен просто блок памяти заданного размера, без вызова конструкторов.
- `new T` выделяет память **и создаёт объект** типа `T`.
- При работе с C API способ освобождения задаёт контракт библиотеки.

Для обычных задач C++ позже будут изучены контейнеры и средства автоматического владения памятью.

### Placement new

Идея: память для объектов резервируется заранее, а когда появляется новый объект, он создаётся в выбранном месте этой памяти **без отдельного выделения**. В примере это точки.

```cpp
// placement-new.cpp
#include <new>
#include <print>

struct Point {
    int x;
    int y;
};

int main() {
    alignas(Point) unsigned char pool[2 * sizeof(Point)];
    Point* first = new (pool) Point{10, 20};
    Point* second = new (pool + sizeof(Point)) Point{30, 40};
    std::println("First: ({}, {}); second: ({}, {})",
                 first->x, first->y, second->x, second->y);

    // The first point is no longer needed: reuse its slot.
    first = new (pool) Point{50, 60};
    std::println("New first: ({}, {})", first->x, first->y);
    // No delete: both objects occupy the automatic buffer pool.
}
```

:::example
Разбор по шагам.

1. Объявляется буфер `pool` размером $2 \cdot \text{sizeof(Point)}$ байт — на две точки. Он автоматический, то есть лежит в стеке.
2. `new (pool) Point{10, 20}` создаёт первую точку в начале буфера (слот 0).
3. `new (pool + sizeof(Point)) Point{30, 40}` создаёт вторую точку в слоте 1: он начинается через `sizeof(Point)` байтов после первого.
4. Печатается `First: (10, 20); second: (30, 40)`.
5. Первая точка больше не нужна, и `new (pool) Point{50, 60}` создаёт на её месте новую. Память слота используется повторно.
6. Печатается `New first: (50, 60)`.
:::

| Слот | Адрес в буфере | Содержимое сначала | Содержимое после повторного использования |
|---|---|---|---|
| 0 | `pool` | `Point{10, 20}` | `Point{50, 60}` |
| 1 | `pool + sizeof(Point)` | `Point{30, 40}` | `Point{30, 40}` |

### Placement new: размер, выравнивание и освобождение

- Буфер вмещает две точки; `alignas(Point)` обеспечивает нужное **выравнивание**.
- Второй слот начинается через `sizeof(Point)` байтов после первого.
- Буфер должен существовать всё время использования точек.
- `delete first` и `delete second` **недопустимы**: слоты принадлежат буферу, а не были выделены через `new`.
- У нашей структуры только поля `int`, поэтому перед повторным использованием слота отдельный вызов деструктора не требуется.

:::note
В полноценном пуле дополнительно учитывают свободные слоты и проверяют, что место есть. В примере показан только механизм создания объектов в готовой памяти.
:::

:::warning
У объектов с ресурсами перед повторным использованием слота может требоваться вызов деструктора. Это будет разобрано вместе с классами.
:::

## Ошибки доступа к памяти и segmentation fault

### Ошибка памяти не обязана завершать программу

Выход за границы массива, использование уничтоженного объекта и разыменование `nullptr` приводят к **неопределённому поведению** (UB).

- Программа может упасть сразу или позже.
- Она может испортить данные или внешне работать правильно.
- Конкретный результат запуска ничего не гарантирует для следующего запуска.

:::remember
Отсутствие падения **не доказывает корректность** программы.
:::

### Segmentation fault

:::meaning
`SIGSEGV` — сигнал ОС при некоторых недопустимых обращениях к памяти, например к неотображённой странице или к странице без нужных прав.
:::

ОС проверяет отображения и права **страниц**, но обычно не знает границы каждого C++-объекта. Поэтому выход за границы массива может остаться внутри доступной страницы и не вызвать `SIGSEGV`.

:::warning
Не всякое неопределённое поведение приводит к `SIGSEGV`, и не всякая ошибка памяти обнаруживается ОС.
:::

### Запись в память только для чтения

Намеренное UB. На типичных Linux/macOS строковый литерал размещается в области без права записи, и попытка записи обычно приводит к аварийному завершению.

```cpp
// write-read-only.cpp
// Intentional undefined behavior: attempting to modify a string literal.
int main() {
    const char* text = "Read-only memory";
    volatile char* writable = const_cast<char*>(text);
    writable[0] = 'r'; // Typically faults on Linux/macOS.
}
```

:::meaning
`const_cast` снимает ограничение **типа**, но не меняет права страницы и не делает изменение литерала допустимым. `volatile` сохраняет попытку записи в обычной сборке; конкретное проявление UB языком не гарантируется.
:::

:::note
Изменяемый массив `char text[]`, инициализированный строкой, хранит отдельную копию символов; запись в такой массив допустима.
:::

### Выход за границы динамического массива

Намеренное неопределённое поведение.

```cpp
// heap-buffer-overflow.cpp
#include <print>

// Intentional undefined behavior.
int main() {
    int* values = new int[3]{10, 20, 30};
    int index = 3;
    std::println("{}", values[index]); // Past the array boundary.
    delete[] values;
}
```

В массиве из трёх элементов допустимы индексы $0$, $1$, $2$. Обращение `values[3]` читает память за последним элементом. Указатель за последним элементом можно **сформировать**, но читать элемент по нему нельзя. AddressSanitizer сообщает об этой ошибке как `heap-buffer-overflow`.

### Обращение после освобождения

Намеренное неопределённое поведение.

```cpp
// use-after-free.cpp
#include <print>

// Intentional undefined behavior.
int main() {
    int* value = new int{42};
    int* alias = value;
    delete value;
    value = nullptr;
    std::println("{}", *alias); // The object no longer exists.
}
```

Здесь два указателя, `value` и `alias`, хранят адрес одного объекта. После `delete value` объект уничтожен, а присваивание `nullptr` переменной `value` не меняет `alias`: он остаётся висячим, и `*alias` — обращение к несуществующему объекту. AddressSanitizer: `heap-use-after-free`.

### Повторное освобождение

Намеренное неопределённое поведение.

```cpp
// double-free.cpp
#include <cstdlib>

// Intentional undefined behavior.
int main() {
    void* memory = std::malloc(16);
    if (memory == nullptr) {
        return 1;
    }
    void* alias = memory;
    std::free(memory);
    std::free(alias); // The same allocation is freed twice.
}
```

Две переменные хранят адрес одного выделенного блока. Освободить блок можно только **один раз**, а второй `free` для того же блока — UB. AddressSanitizer: `double-free`.

### Указатель на объект после выхода из блока

Намеренное неопределённое поведение.

```cpp
// use-after-scope.cpp
#include <print>

// Intentional undefined behavior.
int main() {
    int* pointer = nullptr;
    {
        int local = 42;
        pointer = &local;
    }
    std::println("{}", *pointer); // local's lifetime has ended.
}
```

Переменная `local` — automatic-объект, она существует лишь до конца вложенного блока. Указатель `pointer` пережил блок и хранит адрес уже несуществующего объекта. Байты по этому адресу ещё могут содержать `42`, но объекта `local` уже нет, поэтому чтение — UB. AddressSanitizer: `stack-use-after-scope`.

### Разыменование nullptr

Намеренное неопределённое поведение.

```cpp
// null-dereference.cpp
#include <print>

// Intentional undefined behavior.
int main() {
    int* pointer = nullptr;
    std::println("{}", *pointer);
}
```

`nullptr` не указывает ни на какой объект. UndefinedBehaviorSanitizer сообщает о чтении через нулевой указатель; возможное падение программы — **следствие**, а не определённый языком результат.

### Санитайзеры: проверки во время выполнения

:::meaning
**Санитайзер** — инструмент, который добавляет проверки в программу при сборке и сообщает об ошибках во время её выполнения.
:::

- **AddressSanitizer (ASan)** — выходы за границы, обращение после освобождения, повторное освобождение.
- **UndefinedBehaviorSanitizer (UBSan)** — некоторые виды UB, например разыменование `nullptr`.

Пример команды из корня репозитория, на примере обращения после освобождения:

```bash
clang++ -std=c++23 -Wall -Wextra -pedantic -O0 -g \
  -fsanitize=address,undefined -fno-sanitize-recover=all \
  -fsanitize-address-use-after-scope -fno-omit-frame-pointer \
  examples/05-memory/use-after-free.cpp -o /tmp/memory-error
/tmp/memory-error
```

В отчёте санитайзера указаны: вид ошибки (например, `heap-use-after-free`), строка кода и стек вызовов; для освобождённого блока — места его выделения и освобождения.

:::warning
Проверяется только **выполненный путь**. Успешный запуск под санитайзером не доказывает отсутствие ошибок.
:::

### Утечка памяти — другая ошибка

Если потерять последний доступный указатель на выделенный блок, освободить его обычным способом уже не получится — это **утечка памяти**.

- Сама утечка не обязана приводить к UB или немедленному падению.
- Повторяющиеся утечки увеличивают расход памяти.
- Для поиска утечек есть отдельные проверки; их доступность зависит от платформы.

### Большой локальный массив: риск переполнения стека

:::warning
Это опасный пример: его не следует запускать как обычный. Массив занимает $8$ МиБ, а результат зависит от лимита стека потока.
:::

```cpp
// large-stack-array.cpp
#include <cstdint>
#include <print>

// Dangerous example: this array may exceed the thread's stack limit.
int main() {
    volatile std::uint64_t values[1048576];
    values[10] = 1;
    std::println("{}", static_cast<unsigned long long>(values[10]));
}
```

Массив содержит $1048576$ элементов по $8$ байт, то есть $8$ МиБ, и размещается как локальный объект в стеке потока. Если лимит стека меньше, возможно переполнение стека. `volatile` сохраняет обращения к массиву при оптимизации, но не гарантирует ни конкретный размер кадра, ни падение.
